## [Unreleased]

### Что может задеть при обновлении
- **Новый статус команды `REJECTED_INVALID`** (#139). Поле `type` команды теперь читается: без него или с `TAG_WRITE` — запись
  тега, как раньше; неизвестный `type` (раньше поле не читалось, и такая команда исполнялась как запись) — `REJECTED_INVALID`.
  Если монитор разбирает статусы строгим списком, его нужно дополнить.
- **Новый тип события `PAC_ALARM_COMMAND`** (#139) — исполненная команда над аварией ПЛК.
- **Новый топик `scada.pac-alarms`** (compact, одна партиция; `KAFKA_TOPICS_PAC_ALARMS`) — шлюз создаёт его сам. Без права
  `Create` его создают заранее с `cleanup.policy=compact`; пользователю станции нужно право `Write` в него.
- **Поле `id` контроллера в `controllers.yaml` теперь используется** — это `controllerId` аварий ПЛК (не задан — `name`). На общем
  Kafka оно должно быть уникально между станциями.

### Добавлено
- **Аварии ПЛК (ptusa) для монитора** (#139). У каждого OPC UA-контроллера шлюз раз в `GATEWAY_PAC_ALARMS_INTERVAL_MS` (300 мс)
  читает узел `SYSTEM.ALARMS` фасада `ptusa-opcua` и публикует снимок списка в compact-топик `scada.pac-alarms` (ключ — `id`
  контроллера; `path` — `alarmsPath` контроллера или общее начало имён его тегов), когда изменился список или связь; при обрыве —
  снимок `online: false` с последним списком; у контроллера с `enabled: false` снимок удаляется (tombstone). Команда
  `"type": "PAC_ALARM"` (`ACCEPT`, `SUPPRESS`, `UNSUPPRESS`) в общем топике команд исполняется в очереди контроллера вызовом
  метода фасада `SYSTEM.ALARM_CMD`; в прошивку уходят только целые номера. Настройки — `GATEWAY_PAC_ALARMS_ENABLED`,
  `KAFKA_PUBLISH_PAC_ALARMS`, `KAFKA_TOPICS_PAC_ALARMS`; формат — `docs/MONITOR_INTEGRATION.md`.
- **Симулятор отдаёт аварии, как фасад ptusa-opcua** (узел `SYSTEM.ALARMS`, метод `SYSTEM.ALARM_CMD`, служебный узел
  `SYSTEM.ALARM_RAISE` — завести сообщение) — для интеграционного теста аварий.

## [0.5.0] — 2026-10-22

### Что может задеть при обновлении
- **OPC UA: команда пишется в типе узла, а не по `dataType` тега.** Раньше `INT…` всегда уходил как `Int32`, `FLOAT…` — как `Float`, и
  настоящий ПЛК отклонял запись в узел `Int16`, `UInt16`, `Byte` или `Double` (`BadTypeMismatch` → `FAILED_WRITE`). Теперь тип узла
  шлюз узнаёт при подключении; значение вне диапазона типа — `REJECTED_TYPE_MISMATCH`. На станциях репозитория (`BN1_MCA1`,
  `BN1_NORM_TANKS`) типы тегов и узлов совпадают — для них ничего не меняется.
- **Узел, значение которого шлюз не передаёт (массив, `DateTime`, структура), идёт с качеством `BAD`, а не `null` с `GOOD`.**
- **Тег с неразобранным `nodeId` получает кадры `BAD`** (раньше он молча пропускался, и монитор не получал по нему ничего), команда в
  него — `REJECTED_UNKNOWN_TAG` (раньше `REJECTED_TYPE_MISMATCH`).
- **Новый тип события `CONTROLLER_IDENTITY_MISMATCH`** (#44) — шлюз с `identity` подключился не к тому контроллеру. Если монитор
  разбирает тип события строгим списком, его нужно дополнить. Без `identity` в `controllers.yaml` поведение прежнее.
- **Новый тип события `CONFIG`** в `event_log` и `scada-events` (проблемы с узлами OPC UA). Если монитор разбирает тип события строгим
  списком, его нужно дополнить.
- **Новый статус команды `REJECTED_OUT_OF_RANGE`** (#104) — у тегов с `writeMin`/`writeMax`. Если монитор разбирает статусы строгим
  списком, его нужно дополнить (`docs/MONITOR_INTEGRATION.md`). У тегов без пределов поведение прежнее.

- **OPC UA-фасад `ptusa-opcua` не стартует без настроек защиты** (#50). Раньше он принимал любого: анонимный вход, канал без защиты,
  любые сертификаты клиентов, запись команд в прошивку. Теперь нужен `OPCUA_USERS_FILE` (пользователи с хешем пароля argon2 и ролью
  `read`/`write`) либо явное `OPCUA_ALLOW_ANONYMOUS=true`; канал по умолчанию — `Basic256Sha256_SignAndEncrypt`, сертификаты клиентов
  — только из `trusted/`. Стенды репозитория (`docker-compose.moika.yml`, `docs/monitor/docker-compose.gateway.yml`,
  `scripts/compare_protocols.py`) включают прежнюю открытость явно (`OPCUA_SECURITY=None`, `OPCUA_ALLOW_ANONYMOUS=true`,
  `OPCUA_TRUST_ALL_CLIENTS=true`). Если шлюз боевой станции ходит к фасаду без защиты — задайте ему `security: Basic256Sha256`, логин и
  пароль (`docs/CONFIGURATION.md`) и внесите сертификат шлюза в `trusted/` фасада.

- **`client.id` консьюмера выборов резерва** теперь `scada-gateway-ha-<экземпляр>.st-<отметка станции>` (было
  `scada-gateway-ha-<экземпляр>`) — если на брокере квоты или ACL заданы по `client.id`, их нужно поправить (#108).

### Добавлено
- **Подписки OPC UA вместо опроса** (#101): `acquisition: subscription` у OPC UA-контроллера. Шлюз подписывается на узлы (по подписке на 1000 узлов или меньше,
  если сервер называет меньший предел), сервер присылает только изменения; `samplingInterval` — период тега (`pollingRate` или настройка «период»
  из `channel.tag-settings`). Значения идут в ту же обработку (фильтр «по исключению», история, алармы, команды). Связь — по уведомлениям и
  редкому чтению состояния сервера; обрыв и закрытие подписки сервером — пересоздание сессии с новыми подписками; не удалось создать
  подписки — сеанс идёт опросом (предупреждение и событие `CONFIG`). По умолчанию остаётся `poll`. `scripts/load_check.sh` с
  `ACQUISITION=subscription` меряет оба режима (`docs/STRESS_TEST.md`).
- **Проверка, что шлюз подключился к нужному контроллеру** (#44): поле `identity` у контроллера PAC и OPC UA. При каждом подключении
  шлюз сверяет имя, которым контроллер называет себя сам (PAC — `PAC_name` из handshake; OPC UA — значение узла или
  `ApplicationUri` сервера). Другое имя — соединение закрывается, теги `BAD`, команды в контроллер не уходят, событие
  `CONTROLLER_IDENTITY_MISMATCH` (имена показаны и в экранированном виде — кириллица и латиница неразличимы на глаз), статус в
  `/api/status`. Без `identity` шлюз работает как раньше и при запуске предупреждает, каких контроллеров имя не проверяется.
  `tools/station_config.sh` пишет `identity` при заданном `PAC_NAME`. **Фасад `ptusa-opcua`**: `PAC_NAME` — не соединяться с прошивкой
  с другим именем; узлы `SYSTEM.PAC_NAME` и `SYSTEM.LINK_OK`; `healthcheck` проверяет и связь с прошивкой, а не только порт.
  Симулятор отдаёт те же узлы.
- **Несколько станций на одном Kafka** (#108). Экземпляр не вступает в группу выборов, где уже есть экземпляры другой
  станции (станция — по именам контроллеров, отметка передаётся в `client.id`; экземпляры с общим контроллером — одна
  станция): раньше при общем топике команд активный был бы один на обе станции, и телеметрия одной из них молча
  останавливалась. Ошибка в журнале, событие `HA`/`ERROR`, метрика `scada_ha_foreign_members`, `foreignMembers` в
  `/api/ha`; повторная проверка раз в 30 с, а экземпляр в группе проверяет её состав с тем же периодом. Группа позиций
  команд — настройкой `GATEWAY_COMMANDS_GROUP_ID` (по умолчанию прежняя `scada-gateway-group`, позиции при обновлении
  сохраняются). В `docs/OPERATIONS.md` — пример двух станций, ACL. Тесты: две пары на одном Kafka (у каждой свой
  активный, команды и телеметрия своим путём), экземпляр другой станции в группу не вступает и вступает, когда она
  освободилась.
- **Проверка узлов OPC UA при подключении** (#98). Шлюз читает у сервера таблицу пространств имён и предел `MaxNodesPerRead`, у узла
  каждого тега — тип (`DataType`) и размерность (`ValueRank`). Неразобранные адреса, узлы, которых нет на сервере, массивы,
  неподдерживаемые типы и расхождение `dataType` тега с типом узла — сводкой в журнале (только при изменении, а не на каждом
  переподключении), событием `CONFIG` и в `/api/status` (поле `opcua` контроллера, по 50 тегов на список). Запуск и опрос это не
  останавливает: проблемный тег — `BAD`, остальные работают. Проверка 152 узлов занимает ≈ 50 мс; если сервер не ответил на чтение
  атрибутов — предупреждение и работа как раньше.
- **Адрес `nsu=<URI>;…`** в `nodeId` (#98): номер пространства имён берётся у сервера при каждом подключении — адрес не «уезжает», если
  номер `ns` сменился с новой версией проекта ПЛК.
- **Предел узлов в запросе чтения** (#98): пачка — не больше `MaxNodesPerRead` сервера; если сервер предел не объявил, но ответил
  `BadTooManyOperations`, пачка уменьшается вдвое до конца сессии. Раньше такой сервер давал «обрыв» на каждом цикле.
- **Тест против строгого сервера OPC UA** `tests/opcua_server.rs` (сервер `async-opcua` в том же процессе, без docker; идёт в
  `cargo test`): запись в 12 скалярных типах и отказ при неверном типе, предел запроса 100 узлов на 1000 тегах, неизвестные узлы,
  массивы, `DateTime`, `nsu=`, отчёт в `/api/status` у процесса шлюза.
- **Срок и продление сертификата OPC UA-клиента** (#99). Раньше async-opcua выпускал самоподписанный сертификат на 365
  дней, срок нигде не проверялся, и через год защищённое подключение к ПЛК молча перестало бы устанавливаться. Теперь:
  самоподписанный сертификат выпускается на `GATEWAY_OPCUA_CERT_DAYS` (по умолчанию 5 лет; уже выпущенный не меняется);
  срок — при запуске в журнале, в метрике `scada_opcua_cert_expiry_days`, за `GATEWAY_OPCUA_CERT_WARN_DAYS` (30) дней до
  окончания — предупреждение и событие `SYSTEM` раз в сутки, после окончания — `ERROR`. `scada-gateway opcua-cert`
  показывает сертификат, `scada-gateway opcua-cert renew` перевыпускает (прежняя пара — рядом с суффиксом `.bak`).
  Свой сертификат (например, от УЦ предприятия) — `GATEWAY_OPCUA_CERT_FILE` и `GATEWAY_OPCUA_KEY_FILE`, URI приложения —
  `GATEWAY_OPCUA_APPLICATION_URI`; при запуске шлюз проверяет, что ключ от сертификата и URI совпадает с первым
  альтернативным именем. Документация: том `/app/pki` в примерах запуска, два сертификата у пары резерва, порядок продления.

- **Проверка совместимости с независимым сервером OPC UA** (#100): `tests/opcua_compat.rs` и задание CI `compat` гоняют клиент
  против OPC PLC (стек OPC Foundation .NET): чтение и запись 12 скалярных типов, строгий отказ при неверном типе, проблемные
  узлы, 1200 узлов в пределе `MaxNodesPerRead`, `Basic256Sha256` с паролем и доверием сертификату сервера, восстановление связи
  после остановки сервера.

- **Пределы записи `writeMin`/`writeMax` тега** (#104). Значение команды вне них в ПЛК не уходит — `REJECTED_OUT_OF_RANGE`, пределы в
  `message`. Пределы включительные, можно задать один; проверяется значение оператора (до скрипта канала `write()`, в единицах
  телеметрии), у целого тега — без дробной части, как оно и будет записано. `writeMin` больше `writeMax`, `.nan`/`.inf` или пределы у
  логического или строкового тега — ошибка запуска. Генератор станции берёт пределы из `tools/station-config/overrides.tsv`
  (`limits <вид> <поле> <MIN|-> <MAX|->`); значения заполняет технолог станции — в `BN1_MCA1.yaml` пределов пока нет. В демо-конфиге
  `config/controllers.yaml` пределы 0…1 у двух режимов `M` (OPC UA и PAC) — на них сквозной тест проверяет отказ.

- **Метрики очереди команд** `scada_command_queue{controller}` и `scada_command_wait_seconds{controller}` (#103).

### Исправлено
- **Команды не теряются при временных ошибках Kafka** (#135). Консьюмер команд пересоздавался на любую ошибку приёма, в том
  числе на временную «не удалось соединиться с одним из адресов брокера» (выключенный брокер кластера, `localhost`, который
  разрешается и в IPv6, где брокер не слушает), — а без сохранённой позиции группы новый консьюмер начинал с конца топика, и
  команда, пришедшая между пересозданиями, оставалась без результата. Теперь сетевые ошибки приёма только пишутся в журнал (не
  чаще раза в минуту) — librdkafka переподключается сама; при первом запуске найденный конец топика сразу сохраняется в группе,
  и команда, пришедшая, пока шлюз перезапускался или роль переходила к резерву, исполняется (устаревшая — `REJECTED_EXPIRED`).
  Найдено проверкой релиза: `scripts/stack_smoke.sh` в режиме easydriver изредка не получал результат команды.
- **`KAFKA_CLIENT_*` перекрывает значения продюсера по умолчанию** (#122). Раньше `client.id`, `acks`, `compression.type`, `linger.ms`,
  `batch.size` и `message.timeout.ms` задавались в коде после окружения и молча затирали его (в том числе `KAFKA_CLIENT_BATCH_SIZE` из
  #41). Идемпотентность и свойства групп консьюмеров по-прежнему задаёт шлюз; заданное в окружении значение такого свойства теперь
  не применяется с предупреждением при запуске (`docs/CONFIGURATION.md`).
- **Зависший контроллер задерживал команды всем** (#103). Команды исполнялись строго по одной: запись в контроллер,
  который не отвечает (до `GATEWAY_OPCUA_OP_TIMEOUT_MS` на команду), или пачка уставок с проверкой эффекта держали
  команды остальных контроллеров, и хвост получал `REJECTED_EXPIRED`. Теперь у каждого контроллера своя очередь и свой
  исполнитель: разные контроллеры — параллельно, команды одного — по одной в порядке топика, как раньше. Позиция в топике
  по-прежнему фиксируется до исполнения (не более одного раза). Результаты разных контроллеров приходят в порядке
  исполнения, а не отправки. Тесты: юнит (зависший исполнитель, порядок, перезапуск исполнителя) и `tests/command_queue.rs`
  на процессе шлюза (OPC UA за «молчащим» TCP-прокси — команда PAC исполняется сразу; 20 команд с проверкой эффекта — по
  порядку).
- **Запись OPC UA в узлы не `Int32`/`Float`/`Boolean`/`String` отклонялась настоящим ПЛК** (#97): шлюз приводил значение только по
  `dataType` тега, а сервер OPC UA проверяет тип записи строго. Симулятор и фасад `ptusa-opcua` (библиотека `async-opcua`) тип записи в
  скалярный узел не проверяют, поэтому на стенде ошибка не проявлялась. Значение вне диапазона типа узла (300 в `Byte`) теперь
  отклоняется, а не обрезается сервером.
- **Хороший статус узла без значения шлюз передавал как `null` с `GOOD`** — теперь `BAD`; `UInt64` больше `i64::MAX` тоже `BAD`, а не
  искажённое число.
- **Гонка при первом выпуске сертификата OPC UA.** Контроллеры подключались одновременно, и каждый клиент выпускал свою
  пару: сертификат одного мог остаться с ключом другого (в журнале CI — `Certificate creation failed … already exists`), и
  защищённый канал с такой парой не работал. Теперь сертификат выпускается один раз под общей блокировкой; несовпадение
  ключа с сертификатом — ошибка запуска с подсказкой `opcua-cert renew`.
- **Без PostgreSQL шлюз не запускался** (#105): при запуске он ждал БД минуту и останавливался — перезапуск шлюза при недоступной БД
  оставлял станцию без телеметрии и команд, пара горячего резерва на общей БД останавливалась вся. Теперь БД, не ответившая за 10 с,
  запуск не останавливает: опрос, Kafka и команды по имени работают сразу, миграции и синхронизация тегов — в фоне раз в 5 с, затем
  событие `SYSTEM` «БД подключена…». До этого команды по `tagId` получают `REJECTED_UNKNOWN_TAG`, история и журнал не пишутся
  (счётчик `scada_db_rows_lost_total`), health — `db: DOWN` с причиной в `details.reason`. Неверный пароль, непроверяемый сертификат и
  ошибка миграции по-прежнему останавливают запуск.

### Изменено
- **Имя образа в CI задано явно — `ghcr.io/euzireael/scada_rust`** (#51). Раньше оно бралось из имени репозитория, и после
  переименования репозитория в `SCADA_gateway_rust` образ публиковался бы как новый пакет `scada_gateway_rust` — без доступа у
  тех, кто тянет `scada_rust`. Ссылки на репозиторий (значки в `README.md`, ссылки версий здесь) — на новый адрес.

### Безопасность
- **Защита OPC UA-фасада `ptusa-opcua`** (#50): `OPCUA_SECURITY` (политики через запятую, по умолчанию `Basic256Sha256_SignAndEncrypt`),
  `OPCUA_USERS_FILE` (имя, хеш argon2, роль; `ptusa-opcua hash-password` печатает хеш для пароля со стандартного ввода),
  `OPCUA_ALLOW_ANONYMOUS` (по умолчанию нет), `OPCUA_PKI_DIR` (постоянный каталог, по умолчанию `/var/lib/ptusa-opcua/pki`; в образе —
  `VOLUME`), `OPCUA_TRUST_ALL_CLIENTS` (по умолчанию нет), `OPCUA_CERT_DAYS` (срок сертификата сервера, 3650) и `OPCUA_CERT_HOSTS`
  (имена и адреса в сертификате). Пароль по открытому каналу не принимается; роль `read` читает, а запись получает

- Тип контроллера определяется по схеме адреса, а не по вхождению: `pac://modbus-gw:502` больше не принимается за Modbus.

- Мусор в топике команд усекается в журнале (300 символов) и экранируется.

### Добавлено

## [0.3.0] — 2026-10-05

Шлюз под сбои и под масштаб, безопасность, симулятор и фасад на Rust (Python в репозитории больше нет), условная
логика прошивки в симуляторе. Формат сообщений Kafka, ключи и топики не менялись; новое для монитора —
`docs/MONITOR_INTEGRATION.md` («Что нового для монитора в шлюзе v0.3»), эксплуатация — `docs/OPERATIONS.md`.

### Исправлено

- **Недоставленная телеметрия не теряется молча.** После обрыва брокера значения, которые фильтр
  «по исключению» уже считал отправленными, не доходили до монитора до полной отправки. Теперь, когда
  доставка восстановилась, все теги отправляются заново (`scada_kafka_resyncs_total`); предупреждения о
  недоставленных пишутся раз в 30 с (раньше — по строке на сообщение, тысячи при обрыве).
- **Полная отправка без «залпа».** Первая полная отправка каждого тега смещена на свою долю периода
  (`filter::phase`): на 54 800 тегах вместо одной секунды с десятками тысяч сообщений раз в 30 с —
  ровный поток.
- **Падение задачи не остаётся незамеченным.** Опрос контроллеров, приём команд и фоновые задачи
  перезапускаются надзирателем (`scada_task_restarts_total`, событие SYSTEM/ERROR); отравленный
  мьютекс больше не каскадирует паники.
- **События в Kafka не зависят от БД.** Запись в БД вынесена в отдельную задачу: при недоступной БД
  смена роли пары и обрывы связи уходят в Kafka сразу, а не после таймаута пула. Потерянные из-за БД
  строки считаются (`scada_db_write_errors_total`, `scada_db_rows_lost_total`).
- `/actuator/health` показывает компонент `kafka`.
- **OPC UA-клиент шлюза пробует все адреса имени.** Клиент async-opcua берёт первый адрес из DNS и
  не пробует остальные: `localhost` → `::1` первым, а сервер на `0.0.0.0` слушает только IPv4 —
  шлюз на хосте не подключался (`Could not connect to host [::1]:4840`), хотя `127.0.0.1` отвечал.
  Теперь имя с несколькими адресами проверяется TCP-подключением, и если первый недоступен,
  используется тот, что ответил (в журнале — строка «недоступен — подключаюсь к …»).

### Проверка конфигурации

- Конфигурация контроллеров проверяется целиком при старте: повторяющееся имя тега (ключ Kafka и адрес команды),
  повторяющееся имя контроллера, пустое имя тега и неизвестный протокол в `endpoint` останавливают запуск с
  перечнем проблем (раньше контроллер с неизвестным протоколом молча не опрашивался, а два тега с одним именем
  делали телеметрию и команды неоднозначными). Выключенные контроллеры и теги в расчёт не идут.

### Безопасность OPC UA

- **Защищённое подключение к ПЛК.** `security:` (`Basic256Sha256`, `Aes128_Sha256_RsaOaep`, `Aes256_Sha256_RsaPss`,
  `Basic256`, `Basic128Rsa15`; режим `_Sign` / `_SignAndEncrypt`) и `username:`/`password:` в `controllers.yaml`
  теперь работают — раньше разбирались и молча игнорировались (канал оставался открытым и анонимным). Сертификат сервера
  проверяется по `trusted/` (`GATEWAY_OPCUA_PKI_DIR`, том `/app/pki` в образе);
  `GATEWAY_OPCUA_TRUST_SERVER_CERTS` — только для стенда. Ошибка в `security`, логин без пароля и защита у
  Modbus/PAC останавливают запуск с понятным сообщением; пароль не попадает в журнал и `Debug`.
- Симулятор: `SIM_OPCUA_USER` / `SIM_OPCUA_PASSWORD` включают защищённые конечные точки (Basic256Sha256) — на них
  проверяются политика, режимы, неверный пароль, анонимный вход, цепочка доверия к сертификату сервера.

### Эксплуатация

- `docs/OPERATIONS.md` — настройки, здоровье, метрики и оповещения, что шлюз делает при сбоях.
- `scripts/stack_smoke.sh` — дымовой тест стенда целиком с отказами Kafka, БД и ПЛК.
- `scripts/load_check.sh` (job `load` в CI) — нагрузочная проверка на 27 400 тегах: опрос не отстаёт, нет ошибок доставки и перезапусков задач, память не растёт.

### Симулятор повторяет условную логику прошивки

- Снято с прошивки мойки (все 1816 записываемых каналов станции) и воспроизведено в симуляторе: часть полей прошивка
  **принимает (код 0), но не меняет** (обратная связь, датчики, регистры команд, состояния техобъектов — 107), часть
  **действует только в ручном режиме** (`LINE#V0` — главные клапаны линий, виртуальные выходы, сторожевые таймеры — 18; при
  возврате в автоматику значение возвращается к программе), часть **хранится целой** (16). В `replay_config.yaml` — ключи
  `write: ignore`, `write_requires: {field: M, equals: 1}`, `write_int`, `write_state`. Протокол PAC отвечает как
  прошивка: неизвестное поле известного прибора — код 0, не число — код 1.
- `simulator conformance [host] [port] [config]` проверяет соответствие по driver-master у любого PAC (CI — на симуляторе;
  на прошивке мойки: 81 тег соответствует, 45 пропущено, расхождений 0). Описание — `docs/FIRMWARE_WRITE_BEHAVIOR.md`.

### Изменено

- **PLC-симулятор переписан с Python на Rust** (`simulator/`): OPC UA, Modbus TCP и PAC
  driver-master в одном процессе, тот же `replay_config.yaml`, тот же реплей архива BN1_MCA1
  (формат архива — `data/archive_replay.bin.gz` вместо pickle). Образ — бинарник без интерпретатора,
  узлы OPC UA получают только изменившиеся значения, запись оператора применяется сразу.
  Структура снимка PAC и раскладка регистров Modbus совпадают с прежним симулятором
  (сверено на 63 приборах PAC и 500 регистрах). Новое: поле-массив PAC пишется командой
  `set_cmd('RT_PAR_F', 12, v)` как у настоящего ptusa; `simulator probe-pac` вместо `pac_probe.py`.
  Убраны: синтетические генераторы сигнала (в конфигурации только replay), режим «сырых записей
  приборов» (`sim_records.py`, нужен был Java-шлюзу), `tools/*.py` (`build_archive.py`
  строил архив из SQL-дампа, которого в репозитории нет).

- **OPC UA-фасад `ptusa-opcua/` переписан с Python на Rust** (async-opcua + mlua): те же узлы
  `ns=2;s=<прибор>.<поле>`, те же настройки окружения и порт, запись — `set_cmd` с исходом прошивки
  в статусе записи. Проверен на настоящей прошивке ptusa: 1834 канала GOOD, команда `APPLIED` за
  27 мс, переключение резерва шлюза. Песочница Lua — как в шлюзе (без `os`/`io`/`load`/байткода,
  память 64 МБ, 1 с на снимок), потолок распаковки zlib 8 МБ; вместе с этим закрыт эффект алерта
  GHSA-69v7-xpr6-6gjm (lupa в репозитории больше нет). Python в репозитории не осталось.
  Ограничение: конечные точки GetEndpoints строятся из `OPCUA_BIND` (async-opcua не разделяет
  адрес привязки и анонса); сторонним клиентам OPC UA, которые не пробуют второй адрес `localhost`, вне Docker нужен `OPCUA_BIND=[::]:4840` (шлюз с этим справляется сам, см. «Исправлено»).

### Добавлено

- **Безопасность Kafka**: TLS и SASL (PLAIN, SCRAM) — `KAFKA_SECURITY_PROTOCOL`,
  `KAFKA_SASL_*`, `KAFKA_SSL_*`, любое свойство librdkafka через `KAFKA_CLIENT_*`, Spring-имена
  `SPRING_KAFKA_PROPERTIES_*` (включая JAAS); OpenSSL вшит в бинарник. Секреты не попадают в журнал.
  Проверено на брокере с SASL_PLAINTEXT: неверный пароль — отказ в аутентификации, верный — данные идут.
- **Безопасность REST**: `GATEWAY_API_TOKEN` (или `GATEWAY_API_TOKEN_FILE`) закрывает `/api/*`
  токеном Bearer; `/actuator/health` и `/actuator/prometheus` открыты. `GATEWAY_HTTP_BIND`.
- **Резервирование по здоровью**: активный экземпляр без связи со всеми контроллерами
  (`GATEWAY_HA_YIELD_AFTER_MS`, 30 с) передаёт лидерство партнёру, который в группе, и не отбирает
  его обратно; без партнёра остаётся активным.
