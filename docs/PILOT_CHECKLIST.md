# Пробный запуск на реальном оборудовании

Пошаговый чек-лист: как первый раз подключить шлюз к настоящим контроллерам и монитору, ничего не сломав. Идём
**ступенями**: каждая следующая включает больше возможностей и начинается только после того, как предыдущая прошла по
своим критериям. Безопасность первых ступеней держится на конфигурации, а не на аккуратности: пока у тегов
`writable: false`, шлюз физически не может ничего записать в ПЛК.

## Что должно быть готово

| Что | Проверка |
|---|---|
| Образ нужной версии | `docker pull ghcr.io/euzireael/scada_rust:v0.4.0` (нужен вход: `docs/DEVELOPMENT.md`, «Релиз») |
| Станция описана | `controllers.yaml` с **одним** контроллером, **все теги `writable: false`**, `pollingRate` 1000–2000 мс |
| Сеть | со шлюза открыты порты контроллера (OPC UA 4840, Modbus 502, PAC 10000) и брокера Kafka |
| Время | часы шлюза и монитора синхронизированы по NTP: возраст команды считается по ним, расхождение даст `REJECTED_EXPIRED` |
| Kafka | брокер, топики (см. ниже), доступ только у шлюза и монитора: запись в `scada-commands` равна праву писать в ПЛК |
| Безопасность | `GATEWAY_API_TOKEN` задан, порт 8888 закрыт файрволом, `sslmode=require` к БД — `docs/OPERATIONS.md`, чек-лист |
| OPC UA с защитой | сертификат шлюза внесён в доверенные на ПЛК; сертификат ПЛК переложен из `pki/rejected/` в `pki/trusted/` |
| Кто на связи | человек, который может остановить технологический процесс на самом оборудовании (шлюз не заменяет аварийный останов) |

Не запускать пробу на оборудовании, которое сейчас управляет опасным процессом, пока не пройдены ступени 1–3.

## Как не мешать рабочему монитору

Если рядом работает настоящий монитор, пробный шлюз должен писать в **свои** топики, чтобы не смешивать данные:

```sh
-e KAFKA_TOPICS_TELEMETRY=pilot.tags         -e KAFKA_TOPICS_ALARMS=pilot-alarms \
-e KAFKA_TOPICS_EVENTS=pilot-events          -e KAFKA_TOPICS_COMMANDS=pilot-commands \
-e KAFKA_TOPICS_COMMAND_RESULTS=pilot-command-results \
-e GATEWAY_HA_GROUP_ID=pilot-ha                # только если включено резервирование
```

Шлюз сам создаёт недостающие топики (телеметрия — 3 партиции, алармы — 2, остальные — 1). На ступени 5 монитор
переключается на эти топики на время проверки.

## Ступень 0. Запуск без оборудования

Цель: убедиться, что образ, конфигурация и окружение целы, до того как шлюз коснётся ПЛК.

```sh
docker run --rm -p 8888:8888 -v $PWD/controllers.yaml:/app/config/controllers.yaml:ro \
  -e DB_ENABLED=false -e KAFKA_ENABLED=false -e GATEWAY_API_TOKEN=проба-токен-проба-токен \
  ghcr.io/euzireael/scada_rust:v0.4.0
```

| Проверить | Ожидается |
|---|---|
| Журнал | `SCADA Gateway (Rust) 0.4.0 стартует`, затем `Загружено 1 контроллеров, N тегов` |
| Если иначе | шлюз завершился с текстом причины — `docs/TROUBLESHOOTING.md`, «Шлюз не запускается»; конфигурацию чинить до выезда |
| `curl localhost:8888/actuator/health` | `"status":"UP"`; контроллер `DOWN`, если оборудования рядом нет, — это нормально |
| `curl -H "Authorization: Bearer проба-токен-проба-токен" localhost:8888/api/status` | число тегов совпадает с ожидаемым |

Критерий: запуск без ошибок конфигурации. Дальше — подключать оборудование.

## Ступень 1. Только чтение

Цель: убедиться, что значения читаются верно, и ничего больше. Теги `writable: false`, поэтому даже если в
`scada-commands` придёт команда, шлюз ответит `REJECTED_NOT_WRITABLE`.

Запустите шлюз с Kafka и БД (в пробных топиках, см. выше), оборудование подключено.

| Проверить | Как | Ожидается |
|---|---|---|
| Связь | `GET /actuator/health` | контроллер `UP` в течение 30 с |
| Журнал | `docker logs` | `связь установлена`, нет повторяющихся `Потеряна связь` |
| Метрики | `GET /actuator/prometheus` | `scada_controllers_connected` = `scada_controllers_total`; `scada_task_restarts_total` отсутствует |
| Узлы OPC UA | `GET /api/status`, поле `opcua` контроллера | `unknownNodes`, `unsupportedNodes`, `unresolved` пусты, `typeMismatch` пуст или понятен; иначе — список тегов там же и в журнале (`docs/TROUBLESHOOTING.md`, «OPC UA: проверка узлов при подключении») |
| Качество | считать `scada.tags` (команда ниже) | у большинства тегов `"quality":"GOOD"`; доля `BAD` понятна (тег выключен в ПЛК или не существует) |
| Значения | сверить 5–10 тегов с панелью ПЛК или инженерным ПО | числа совпадают, типы верны (целое — целое, вещественное — вещественное) |

```sh
kafka-console-consumer.sh --bootstrap-server БРОКЕР --topic pilot.tags --from-beginning \
  --property print.key=true --max-messages 20
```

Сообщения идут редко: публикация «по исключению» (при изменении и раз в 30 с) — это норма, не зависание. Для проверки
можно временно задать `GATEWAY_PUBLISH_ENABLED=false`: тогда каждый тег уходит каждый цикл.

**Критерий:** 15 минут без `BAD` у тегов, которые должны быть живыми; значения совпадают с эталоном.
**Если `BAD`:** `docs/TROUBLESHOOTING.md`, «Нет связи с контроллером» (адрес узла, `deviceName`/`fieldName`, `modbusAddress`).

## Ступень 2. Нагрузка на контроллер

Цель: убедиться, что опрос не мешает самому ПЛК. Реальные контроллеры бывают слабее эмулятора.

1. Оставьте `pollingRate` 1000–2000 мс. Если нужна частота выше, снижайте период ступенями (2000 → 1000 → 500) и после
   каждой смотрите ниже.
2. Наблюдайте 30 минут.

| Метрика | Хорошо | Плохо |
|---|---|---|
| `scada_poll_seconds` (гистограмма) | значительно меньше периода опроса | растёт вровень с периодом |
| `scada_poll_overruns_total` | не растёт | растёт: шлюз не успевает; увеличьте период или уменьшите число тегов |
| Время цикла на панели ПЛК | не изменилось | выросло: нагрузка заметна — период увеличить |
| `process_resident_memory_bytes` | стабильна | постоянно растёт |

**Критерий:** метрики спокойны, цикл ПЛК не изменился. **Если ПЛК стал медленнее — остановить шлюз и увеличить период.**

## Ступень 3. Сбои

Делается только с согласия владельца оборудования и в безопасное время. Цель: убедиться, что при обрыве шлюз ведёт
себя как описано, а после возвращения всё восстанавливается само.

| Сбой | Как сделать | Ожидается |
|---|---|---|
| Пропал контроллер | отключить кабель от ПЛК или закрыть порт на файрволе на 1–2 минуты | в течение `GATEWAY_STALE_AFTER_MS` (30 с) контроллер `DOWN`, по тегам идут кадры `BAD`, событие `CONNECTION`; после возврата — `UP`, `GOOD`, событие «связь восстановлена» |
| Пропал брокер Kafka | остановить Kafka на 1 минуту | шлюз жив, опрос идёт; `scada_kafka_send_errors_total` растёт; после возврата растёт `scada_kafka_resyncs_total` и в топике снова все теги |
| Пропала БД | остановить PostgreSQL на 30 с | телеметрия и опрос идут; `db: DOWN` в health, потом `UP`; строки журнала на время потеряны (`scada_db_rows_lost_total`) |
| Перезапуск шлюза | `docker restart` | старт < 1 с до опроса, все теги отправлены заново |

**Критерий:** каждый сбой проходит как в таблице, шлюз ни разу не упал сам.

## Ступень 4. Запись одного тега

Цель: проверить запись, ничем не рискуя. **Выберите тег, запись в который безопасна**: уставка, параметр, которым
не управляется движение или нагрев. Не клапан и не привод.

1. Согласуйте тег и значение с технологом; запишите текущее значение, чтобы вернуть.
2. В `controllers.yaml` поставьте `writable: true` **только у этого тега**, перезапустите шлюз (горячей перезагрузки
   конфигурации нет).
3. Включите проверку эффекта (OPC UA и PAC): `-e GATEWAY_COMMANDS_VERIFY_MS=1500` — шлюз перечитает значение и скажет, подействовала ли
   запись.
4. Отправьте команду:

```sh
echo '{"commandId":"pilot-1","tagName":"ПОЛНОЕ.ИМЯ.ТЕГА","value":42,"requestedBy":"pilot"}' | \
  kafka-console-producer.sh --bootstrap-server БРОКЕР --topic pilot-commands
kafka-console-consumer.sh --bootstrap-server БРОКЕР --topic pilot-command-results --from-beginning \
  --property print.key=true --max-messages 5
```

| Результат | Что значит |
|---|---|
| `APPLIED` | ПЛК принял запись; сверьте значение на панели ПЛК и в `scada.tags` |
| `FAILED_NOT_APPLIED` | принял, но значение не изменилось (программа не разрешает действие); для PAC этот статус недоступен — код 0 значит «принято», проверять по значению |
| `REJECTED_NOT_WRITABLE` | тег не `writable` или это Modbus (Modbus не пишется никогда) |
| `REJECTED_TYPE_MISMATCH` | значение не приводится к типу тега |
| `REJECTED_EXPIRED` | команда старше `GATEWAY_COMMANDS_MAX_AGE_MS`: проверьте часы |
| `FAILED_NO_CONNECTION`, `FAILED_WRITE` | связи нет или сервер отклонил запись; подробности в `message` и журнале |

5. **Верните прежнее значение** второй командой и убедитесь, что оно вернулось.
6. Повторите команду с тем же `commandId` в течение минуты: повтор должен быть отброшен (в журнале «уже обработана недавно»).

**Критерий:** `APPLIED` с видимым эффектом на оборудовании, возврат значения, повтор отброшен. Затем выключите
`writable` у тега, пока не начата ступень 5.

**Для PAC-массивов и менеджера рецептов** (`RT_PAR_F[n]`, `RECMAN[n]`): запись в поле-массив уходит как
`set_cmd('RT_PAR_F', n, v)`, а в `RECMAN` — в особом формате (`docs/CONFIGURATION.md`, «Запись в PAC»). Формат
`RECMAN` проверен только по описанию прошивки, на настоящем контроллере — нет. Пробуйте его на безвредном рецепте и
сообщите результат; с ним пройдёт то же `APPLIED`, а ошибки проявятся как `FAILED_WRITE` либо отсутствием эффекта.

## Ступень 5. Монитор

Цель: проверить полный круг с настоящим монитором (его сопровождает разработчик монитора).

1. Направьте монитор на пробные топики (или остановите рабочий шлюз и верните стандартные имена, если станция одна).
2. Проверьте телеметрию: теги появились в мониторе, графики идут, `BAD` отображается как «нет данных».
3. Проверьте обрыв: повторите сбой из ступени 3 и посмотрите, как его показывает монитор.
4. Командой из интерфейса монитора повторите запись ступени 4 на том же безопасном теге. Результат должен вернуться
   оператору как `APPLIED`; монитор не должен показывать `NO_CONFIRMATION`.
5. Проверьте настройку `runtime.telemetry.max-silence-ms` монитора: она должна быть больше `GATEWAY_PUBLISH_FULL_RESEND_MS`
   (30 с), иначе монитор будет считать неизменные теги «замолчавшими».

**Критерий:** телеметрия, обрыв и команда проходят через монитор так же, как проходили на ступенях 1–4 в Kafka.

## Ступень 6. Прогон на сутки

Цель: поймать то, что проявляется только со временем (утечки, редкие сбои, дрейф часов).

* 24 часа без вмешательства, при желании — пара резервирования (`GATEWAY_HA_ENABLED=true`, два экземпляра).
* Раз в несколько часов смотреть и записывать:

| Что | Хорошо |
|---|---|
| `process_resident_memory_bytes` | не растёт со временем |
| `scada_task_restarts_total` | отсутствует |
| `scada_poll_overruns_total` | не растёт |
| `scada_kafka_send_errors_total`, `scada_db_rows_lost_total`, `scada_events_dropped_total` | не растут вне запланированных сбоев |
| `GET /api/events/severity/ERROR` и `CRITICAL` | пусто или объяснимо |
| `scada_ha_active` (если пара) | ровно один экземпляр равен 1 |

**Критерий:** сутки без перезапусков задач, без роста памяти, без необъяснимых `BAD`.

## Когда остановиться

Остановите шлюз (`docker stop`) и не продолжайте, пока причина не ясна, если:

* контроллер стал заметно медленнее или перегружен;
* запись изменила не то, что ожидалось, или изменила что-то, не относящееся к тегу;
* значения не совпадают с эталоном и разница не объясняется (тип, масштаб);
* шлюз перезапускает задачи (`scada_task_restarts_total`) или падает;
* память растёт постоянно;
* что-то в поведении оборудования вызывает сомнение: **сначала остановить шлюз, потом разбираться**.

Остановка безопасна: шлюз отдаёт `BAD`, команды в ПЛК не уходят, ПЛК продолжает работать по своей программе.

## Что собрать для разбора

Если что-то пошло не так, приложите:

* версию шлюза (первая строка журнала) и дату;
* `docker logs --tail 500` и вывод `GET /actuator/health`, `GET /api/status`;
* `GET /actuator/prometheus` (строки `scada_*`);
* фрагмент `controllers.yaml` **без паролей** (контроллер и несколько проблемных тегов);
* для PAC — вывод `simulator probe-pac хост порт` (handshake, объектная модель и снимок);
* что именно делали и во сколько.

## Откат

1. `docker stop scada-gateway` — шлюз остановлен, ничего не пишет.
2. Если на ступени 4 менялось значение, верните его в ПЛК штатным способом.
3. Если монитор был переключён на пробные топики — верните прежние.
4. `writable: true` в `controllers.yaml` не оставлять: после пробы снова `false` у всех тегов.
