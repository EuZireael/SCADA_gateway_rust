# Подключение монитора к шлюзу на эмуляторе мойки

Для того, кто делает монитор (`scada-editor-backend`). Что изменилось, как запустить и что
проверить. Контракт Kafka прежний (топики, тело `{value, quality, timestamp}`, статусы команд) —
изменились **источник данных** и **имена каналов**.

## Что это

Шлюз теперь читает станцию **только по OPC UA**. Данные даёт **эмулятор мойки**: настоящая
прошивка ptusa с проектом станции BN1-МСА1 (без модулей ввода-вывода, логика станции живая).

У прошивки есть собственный OPC UA-сервер, но он отдаёт только `<прибор>.state/.value` — 22 %
каналов, без режимов `M`, уставок, технологических объектов и `SYSTEM`, и запись `state` на
прибор не действует. Поэтому между прошивкой и шлюзом стоит **фасад** (`ptusa-opcua/`) — маленькая
программа-переводчик. Она берёт у прошивки её родным протоколом (driver-master) **всё** и
выставляет как OPC UA-сервер; запись клиента превращает в команду прошивке.

```
прошивка ptusa  ←driver-master→  фасад  ←OPC UA :4840→  шлюз  →Kafka→  монитор
 (проект BN1-МСА1)               (переводчик)
```

Со стороны шлюза и монитора фасад — обычный OPC UA-сервер станции.

## Что изменилось для монитора

| | Было (Python-симулятор) | Стало |
|---|---|---|
| Источник | симулятор, 3 контроллера, 2517 каналов | прошивка ptusa, 1 контроллер, **1834 канала** |
| Имя канала (Kafka-key) | `Барановичи-1.BN1_MCA1.V_ST_1.LINE1V0.ST` | **`Барановичи-1.BN1_MCA1.LINE1.V0.ST`** — объектный путь вашей базы каналов |
| Запись | только команды и уставки | **все числовые каналы** (1816 из 1834), строки — только чтение |
| Обрыв связи | значение замирало | кадр `value=null, quality=BAD` (`GATEWAY_SEND_BAD_FRAMES=true`) |

**Ключи изменились — проекты, привязанные к старым ключам, нужно перепривязать.** Новые ключи
строятся вашим же кодом импорта `.cdbx` (`CdbxParser`, `PlcProjectParser`, `ObjectPathMapper`):
если импортировать `BN1 MCA1 NEW.cdbx` с площадкой `Барановичи-1` и проектом `BN1_MCA1`, дерево
каналов совпадёт с ключами телеметрии.

## Что нового для монитора в шлюзе v0.3

Формат сообщений, ключи и топики **не менялись**. Что стоит знать:

- **Статус команды `REJECTED_EXPIRED`.** Команда, пролежавшая в `scada-commands` дольше
  `GATEWAY_COMMANDS_MAX_AGE_MS` (30 с; шлюз стоял или не успевал), в ПЛК **не уходит** — результат
  `{"status":"REJECTED_EXPIRED","success":false}`. Возраст считается по метке записи Kafka, иначе по `timestamp` в теле
  команды (ISO-8601, как шлёт `CommandProducer`). `CommandOutcome.fromGateway` пропускает любой статус как строку, но
  интерфейс, который разбирает статусы по списку, стоит дополнить.
- **Статус `FAILED_NOT_APPLIED` (по желанию, выключен).** При `GATEWAY_COMMANDS_VERIFY_MS` > 0 шлюз после записи
  по OPC UA перечитывает узел, по PAC — запрашивает свежий снимок; если ПЛК принял команду (код 0), но значение не изменилось (программа не разрешает
  действие, например клапан не в ручном режиме), результат — `{"status":"FAILED_NOT_APPLIED","success":false}`.
  Без этой переменной поведение прежнее: `APPLIED` означает «ПЛК принял запись».
- **Команды «не более одного раза».** Позиция в `scada-commands` коммитится до исполнения; повтор того же `commandId`
  отбрасывается. Результат по таймауту монитора — `NO_CONFIRMATION` — по-прежнему значит «неизвестно».
- **Полная отправка раз в `full-resend-ms` разнесена по времени**: первая — через долю периода (у каждого тега своя),
  дальше раз в период. Интервал между публикациями тега не длиннее `full-resend-ms`, поэтому
  `runtime.telemetry.max-silence-ms` > `full-resend-ms` по-прежнему гарантирует «тег жив».
- **После сбоя брокера шлюз сам отправляет все теги заново** (как только доставка восстановилась), а не ждёт полной
  отправки: монитору не нужно ничего делать при перезапуске Kafka.
- **Горячее резервирование**: две копии шлюза с `GATEWAY_HA_ENABLED=true`; переключение при отказе ≈ session-timeout,
  новый активный сразу шлёт значения всех тегов; в `scada-events` событие `HA` (`details.instance`, `details.role`).
- **События SYSTEM/ERROR** — задача шлюза упала и перезапущена; `/actuator/health` содержит компоненты `db`, `kafka`,
  `controllers`. Метрики и оповещения — `docs/OPERATIONS.md`.
- **Безопасность**: Kafka по TLS/SASL (`KAFKA_SECURITY_PROTOCOL`, `KAFKA_SASL_*`), `/api/*` под токеном
  (`GATEWAY_API_TOKEN`), OPC UA с политикой и пользователем (`security:`, `username:`, `password:` в `controllers.yaml`).
- **Масштаб**: 54 800 тегов (20 × 2740, ≈ 18 000 изменений/с) — ≈ 25 % одного ядра и ≈ 125 МБ; 27 400 тегов — ≈ 10 %
  ядра и ≈ 75 МБ (`scripts/load_check.sh`, проверяется в CI).

## Что нужно

- Docker (на Windows — Docker Desktop, Linux-контейнеры). Шлюз — на Rust: образ собирается из
  `Dockerfile` репозитория (первая сборка — минуты), JDK и Maven не нужны.
- **Папка проекта ПЛК** станции (`BN1-CIP1`: `main.plua`, `main.io.lua`, `main.objects.lua`…) **вместе с
  подмодулем `bin/`** (`git submodule update --init` в папке проекта; нужен
  `bin/linux-default/Release/ptusa_main`). Проект проприетарный — в репозиторий шлюза не входит.
- Этот репозиторий (Rust-шлюз; в нём `ptusa-opcua/` и `config/stations/`).

## Запуск в вашем стенде (docker-compose монитора)

1. Скопируйте `docs/monitor/docker-compose.gateway.yml` из этого репозитория поверх вашего
   `docker-compose.gateway.yml` (симулятор заменён на `scada-ptusa` + `scada-opcua`, шлюз берёт
   `config/stations/BN1_MCA1.yaml`; Kafka, топики и кадры BAD — как у вас).
2. Запустите (PowerShell; образы фасада и шлюза соберутся сами):
   ```powershell
   $env:MOIKA_PROJECT = "C:/путь/к/BN1-CIP1"        # прямые слэши
   $env:SCADA_GATEWAY_PATH = "C:/путь/к/scada-gateway"
   docker compose -f docker-compose.yml -f docker-compose.gateway.yml up -d
   ```

## Запуск, если шлюз у вас на хосте (как в `start-all.ps1`)

В Docker поднимаются только прошивка и фасад; шлюз, Kafka и Postgres — ваши. Шлюз — один
исполняемый файл: `cargo build --release` (нужен stable Rust (edition 2024) и C-компилятор с cmake для
librdkafka) → `target/release/scada-gateway`, либо образ `docker build -t scada-gateway .`.

```powershell
cd C:/путь/к/scada-gateway
$env:MOIKA_PROJECT = "C:/путь/к/BN1-CIP1"
docker compose -f docker-compose.moika.yml up -d --build ptusa ptusa-opcua      # OPC UA станции: localhost:4840
```

и вместо запуска Python-симулятора и java-шлюза запускать Rust-шлюз с переменными окружения:

```powershell
$env:CONTROLLERS_YAML = "C:/путь/к/scada-gateway/config/stations/BN1_MCA1.yaml"
$env:PLC_HOST = "localhost"
$env:SPRING_KAFKA_BOOTSTRAP_SERVERS = "localhost:9092"
$env:SPRING_DATASOURCE_URL = "jdbc:postgresql://localhost:5433/scada_db"   # + _USERNAME/_PASSWORD
$env:GATEWAY_SEND_BAD_FRAMES = "true"
$env:GATEWAY_SCRIPTS_DIR = "C:/путь/к/scada-gateway/config/scripts"
.\target\release\scada-gateway.exe
```

Имена переменных — те же, что у Java-шлюза (`SPRING_*`, `KAFKA_TOPICS_*`, `GATEWAY_*`), их
полный список — в README.

Linux/macOS: `MOIKA_PROJECT=… ./up-moika.sh plc` — то же самое и печатает нужные переменные.
Весь стенд целиком (прошивка + фасад + шлюз + Kafka на :9094 + Postgres): `MOIKA_PROJECT=… ./up-moika.sh`.

Порты: `4840` OPC UA станции, `10100` driver-master прошивки (отладка), `8888` шлюз. Если у вас
ещё запущен Python-симулятор — он занимает `4840`: остановите его.

## Как проверить

- `curl localhost:8888/actuator/health` → `{"status":"UP"}`; в логе шлюза `связь установлена`
  по контроллеру станции.
- В `scada.tags` — 1834 ключа, все `GOOD`.
- Команда в `scada-commands` `{"commandId":…,"tagName":"Барановичи-1.BN1_MCA1.LINE1.V0.M","value":1}` →
  в `scada-command-results` статус `APPLIED`, и значение возвращается в телеметрию.
- Остановите контейнер `scada-ptusa` — через ~10 с в журнале `DISCONNECTED`, значения приходят
  как `BAD`; запустите — через ~15 с `CONNECTED`.

## Публикация «по исключению»

Шлюз по умолчанию шлёт тег в Kafka только при изменении (и раз в `GATEWAY_PUBLISH_FULL_RESEND_MS`,
30 с, — полная отправка всех тегов, чтобы после перезапуска монитор получил всё). Контракт —
`docs/TELEMETRY_BY_EXCEPTION.md`; на стороне монитора `runtime.telemetry.max-silence-ms` (40 с)
должен быть больше `full-resend-ms`. Значения на плоской эмуляции почти не меняются, так что
поток в `scada.tags` после первой отправки редкий — это норма, а не зависание.

## Настройки тегов из `channel`

Шлюз читает сжатый топик `channel.tag-settings` (его создаёт и пишет `channel`) и применяет настройки тегов без перезапуска: «Период» опроса
(тег реже цикла) и «Дельта» (зона нечувствительности локальной истории). Состав тегов, `writable`, адресация и фильтр «по исключению» не меняются.
Подробности и переменные — `docs/CONFIGURATION.md`, раздел «Настройки тегов из channel».

## Горячее резервирование и скрипты

- Два экземпляра шлюза с `GATEWAY_HA_ENABLED=true` и общим брокером: активный публикует и
  принимает команды, резерв опрашивает контроллеры и молчит; при отказе активного резерв
  становится активным за ≈2 с и сразу шлёт все теги. Состояние — `GET /api/ha`.
- Пользовательские Lua-скрипты обработки значений (`config/scripts/`, привязка по маскам тегов в
  `scripts.yaml`): монтируются томом, правки подхватываются без перезапуска. Список — `GET /api/scripts`.

## Что нужно знать

- Команды каждого контроллера исполняются по порядку, разных контроллеров — параллельно: результаты в
  `scada-command-results` приходят в порядке исполнения, а не отправки. Сопоставлять их — по `commandId`.
- Всего в базе каналов 2647 канала: **813 выключены** — их объекта нет в проекте ПЛК (OBJECT4–6,
  сторожевые таймеры со старыми именами, поля, которых у прибора нет). Прошивка их не отдаёт.
- В прошивке есть ещё ~300 значений, которых нет в базе каналов (`ACID_PAR`, `CAUSTIC_PAR`,
  диагностика датчиков…): у них нет имён, под которыми их знает монитор.
- Прошивка принимает команду (`APPLIED`), но значение не всегда меняется: 107 полей считает программа (запись игнорируется), 18 действуют только в ручном режиме (главные клапаны линий `LINE#V0`), 16 хранятся целыми. Подробности — `docs/FIRMWARE_WRITE_BEHAVIOR.md`.
- `RT_PAR_F[12]` прошивка хранит целым: 7.5 станет 7.
- **Значения датчиков нулевые, графики плоские** — это не ошибка. Эмулятор запущен без ввода-вывода
  (`--no_io`), физического процесса нет; значения — ровно то, что отдаёт прошивка. Живые числа
  появляются, когда их записать (командой из монитора или через `scada-commands` — писать можно
  во все числовые каналы) или когда станция выполняет операцию. Архива в эмулятор не подмешивается.
  На настоящем ПЛК запись в показание датчика перезатрётся сканированием входов.

## Если не запускается

| Симптом | Причина |
|---|---|
| `scada-ptusa` unhealthy, в логе `ptusa_main: not found` | нет подмодуля `bin` в папке проекта: `git submodule update --init` |
| `required variable MOIKA_PROJECT is missing` | не задан `MOIKA_PROJECT` |
| порт `4840`/`8888`/`5433` занят | запущен старый симулятор/шлюз/Postgres |
| шлюз: `нет файла … controllers` / `PLC_HOST` не разрешён | не заданы `CONTROLLERS_YAML` и `PLC_HOST` |
| в Docker Desktop проект не монтируется | путь не в списке общих папок; используйте прямые слэши |

Устройство фасада и результаты проверки — `ptusa-opcua/README.md`.
