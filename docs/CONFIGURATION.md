## Как читаются настройки

* Настройки берутся **только из окружения** и `controllers.yaml`; других файлов настроек нет. Изменение любой из них
  требует перезапуска (кроме скриптов — они перечитываются сами).
* Имена совпадают с именами Java-шлюза (Spring relaxed binding), поэтому его `docker-compose` работает без правок.
  Для многих настроек есть второе имя без подчёркиваний (`GATEWAY_COMMANDS_MAXAGEMS` = `GATEWAY_COMMANDS_MAX_AGE_MS`) —
  оно принимается, но в новых развёртываниях пользуйтесь основным.
* Пустое значение переменной считается незаданным. Логические значения: `true`, `1`, `yes`, `on` — «да»,
  всё остальное — «нет». Время — в миллисекундах, если не сказано иное.
* **Неверное число или неверный режим останавливают запуск** с текстом, какая переменная не так (молча подставить
  значение по умолчанию значило бы работать не так, как задумал оператор).
* `controllers.yaml` перед разбором проходит подстановку `${ИМЯ:значение}` и `${ИМЯ}` (обязательная — без неё ошибка).

## Переменные окружения

### Общие и HTTP

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CONTROLLERS_YAML` (или `CONTROLLERS_CONFIG`) | `config/controllers.yaml` | путь к файлу станции; форма `file:/путь` из Java понимается |
| `SERVER_PORT` | `8888` | порт HTTP (`/actuator/*`, `/api/*`) |
| `GATEWAY_HTTP_BIND` (или `SERVER_ADDRESS`) | `0.0.0.0` | адрес привязки HTTP; `127.0.0.1` — только локально |
| `GATEWAY_API_TOKEN` | — | токен REST: `/api/*` требует `Authorization: Bearer <токен>`; без токена открыт (в журнале предупреждение). Короче 16 символов — тоже предупреждение. `/actuator/*` токеном не закрывается |
| `GATEWAY_API_TOKEN_FILE` | — | то же, токен из файла (секреты Docker); пустой файл — ошибка запуска |
| `RUST_LOG` | `info,…` | уровни журнала в формате `tracing-subscriber` (`debug`, `scada_gateway::kafka=debug`) |
| `SIM_HOST`, `SIM_PAC_PORT`, `PLC_HOST`, `PLC_PORT` и любые другие | — | не настройки шлюза, а переменные для `${…}` в `controllers.yaml` (в станции репозитория `SIM_PAC_PORT` — порт PAC симулятора, по умолчанию 10000; задайте, если он занят настоящим `ptusa_main`) |

### База данных (PostgreSQL)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DB_ENABLED` | `true` | `false` — шлюз без БД: журнал и история не пишутся, команды только по имени тега |
| `SPRING_DATASOURCE_URL` (или `DB_URL`) | `jdbc:postgresql://localhost:5433/scada_db` | адрес БД. Понимаются `jdbc:postgresql://`, `postgresql://`, `postgres://`; из параметров — `sslmode`, `sslrootcert`, `ssl`; остальные игнорируются с предупреждением |
| `SPRING_DATASOURCE_USERNAME` (или `DB_USERNAME`) | `scada_user` | пользователь |
| `SPRING_DATASOURCE_PASSWORD` (или `DB_PASSWORD`) | `scada_password` | пароль; **смените** (шлюз с паролем по умолчанию запустится) |
| `DB_SSLMODE` | `prefer` | `disable`, `allow`, `prefer`, `require`, `verify-ca`, `verify-full`; сильнее `sslmode` в адресе |
| `DB_SSLROOTCERT` | системные | файл корневого сертификата УЦ сервера БД; сильнее `sslrootcert` в адресе |

`ssl=true` в адресе означает `verify-full`, `ssl=false` — `disable` (как в драйвере JDBC); явный `sslmode` сильнее.
На объекте — `require` или строже.

### Kafka

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `KAFKA_ENABLED` | `true` | `false` — без Kafka (опрос идёт, наружу ничего не уходит; несовместимо с `GATEWAY_HA_ENABLED`) |
| `SPRING_KAFKA_BOOTSTRAP_SERVERS` (или `KAFKA_BOOTSTRAP_SERVERS`) | `localhost:9092` | брокеры |
| `KAFKA_TOPICS_TELEMETRY` | `scada.tags` | телеметрия |
| `KAFKA_TOPICS_ALARMS` | `scada-alarms` | алармы |
| `KAFKA_TOPICS_EVENTS` | `scada-events` | события |
| `KAFKA_TOPICS_COMMANDS` | `scada-commands` | команды (читаются) |
| `KAFKA_TOPICS_COMMAND_RESULTS` | `scada-command-results` | результаты команд |
| `KAFKA_TOPICS_PAC_ALARMS` | `scada.pac-alarms` | снимки аварий ПЛК; шлюз создаёт его compact (`cleanup.policy=compact`) с одной партицией — заранее создаваемый топик тоже должен быть compact, см. [ниже](#аварии-плк-ptusa) |
| `CHANNEL_TAG_SETTINGS_TOPIC` | `channel.tag-settings` | настройки тегов от `channel` (читаются; шлюз топик не создаёт), см. [ниже](#настройки-тегов-из-channel) |
| `GATEWAY_TAG_SETTINGS_ENABLED` | `true` | применять ли настройки тегов из этого топика; без топика теги работают по YAML |
| `KAFKA_TOPICS_REPLICATION` | `1` | фактор репликации топиков, которые шлюз создаёт сам (на кластере — по числу брокеров). Существующие топики он не трогает |
| `KAFKA_PUBLISH_EVENTS` | `true` | публиковать события в Kafka |
| `KAFKA_PUBLISH_ALARMS` | `true` | публиковать алармы в Kafka |
| `KAFKA_PUBLISH_PAC_ALARMS` | `true` | публиковать снимки аварий ПЛК |
| `KAFKA_SECURITY_PROTOCOL` | — | `PLAINTEXT`, `SSL`, `SASL_PLAINTEXT`, `SASL_SSL` |
| `KAFKA_SASL_MECHANISM` | — | `PLAIN`, `SCRAM-SHA-256`, `SCRAM-SHA-512` (Kerberos/GSSAPI не поддерживается) |
| `KAFKA_SASL_USERNAME`, `KAFKA_SASL_PASSWORD` | — | учётные данные SASL |
| `KAFKA_SSL_CA_LOCATION` | — | корневой сертификат брокера |
| `KAFKA_SSL_CERTIFICATE_LOCATION`, `KAFKA_SSL_KEY_LOCATION`, `KAFKA_SSL_KEY_PASSWORD` | — | клиентский сертификат и ключ (mTLS) |
| `KAFKA_CLIENT_<СВОЙСТВО>` | — | любое свойство librdkafka: `KAFKA_CLIENT_SSL_ENDPOINT_IDENTIFICATION_ALGORITHM=none` → `ssl.endpoint.identification.algorithm`; перекрывает именованные и значения продюсера по умолчанию (`client.id`, `acks`, `compression.type`, `linger.ms`, `batch.size`, `message.timeout.ms`: `KAFKA_CLIENT_BATCH_SIZE=250000`). Неизвестное свойство останавливает запуск; свойства, которые шлюз задаёт сам (см. ниже), игнорируются с предупреждением |
| `SPRING_KAFKA_PROPERTIES_SECURITY_PROTOCOL`, `…_SASL_MECHANISM`, `…_SASL_JAAS_CONFIG` | — | как у Java-шлюза; из JAAS берутся `username` и `password` |

**Что `KAFKA_CLIENT_*` не перекрывает.** Идемпотентность продюсера (`enable.idempotence=true`: от неё порядок и отсутствие дублей при
повторной отправке), а у консьюмеров команд, настроек тегов и выборов резерва — `group.id`, `enable.auto.commit`,
`auto.offset.reset`, `allow.auto.create.topics`, `session.timeout.ms`, `heartbeat.interval.ms`, `max.poll.interval.ms` и
`partition.assignment.strategy`: группа, позиции и состав группы выборов определяются настройками `GATEWAY_COMMANDS_GROUP_ID` и
`GATEWAY_HA_*`. Заданное в окружении значение такого свойства не применяется, шлюз пишет об этом предупреждение при запуске. Другие
значения по умолчанию перекрываются, но не все сочетания допустимы для librdkafka: например, `acks=1` вместе с идемпотентным
продюсером он отвергнет, и шлюз не запустится — с понятной ошибкой.

Пароли и ключи в журнал и `Debug` не попадают. Свойства безопасности применяются ко всем клиентам шлюза: продюсеру,
консьюмеру команд, консьюмеру выборов и администратору топиков.

### Контроллеры и связь

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GATEWAY_OPCUA_OP_TIMEOUT_MS` | `5000` | таймаут операции OPC UA (подключение, чтение, запись) |
| `GATEWAY_MODBUS_OP_TIMEOUT_MS` | `3000` | таймаут операции Modbus |
| `GATEWAY_PAC_OP_TIMEOUT_MS` | `3000` | таймаут операции PAC |
| `GATEWAY_STALE_AFTER_MS` | `30000` | нет удачных чтений дольше — связь считается потерянной, сессия OPC UA пересоздаётся |
| `GATEWAY_SUPERVISE_INTERVAL_MS` | `200` | пауза между попытками подключения к OPC UA после обрыва; первые 300 неудачных попыток (≈ минута) идут с этой паузой, дальше не реже раза в 2 с (чтобы журнал не рос при многодневной недоступности). Так быстро повторяется только потеря связи; после отказа сервера (неверный пароль, защита, лимит сессий) пауза не короче 2 с. Чем короче пауза, тем быстрее возврат связи после обрыва; у контроллеров с малым числом одновременных OPC UA-сессий (на симуляторе это не проверялось) паузу не делайте короче 0,2 с |
| `GATEWAY_HEALTH_LOG_INTERVAL_MS` | `60000` | как часто писать в журнал сводку «кто на связи» |
| `GATEWAY_HEARTBEAT_INTERVAL_MS` | `30000` | как часто слать событие `HEARTBEAT` |
| `GATEWAY_OPCUA_PKI_DIR` | `<tmp>/scada-gateway-pki` | хранилище сертификатов OPC UA (`own/`, `private/`, `trusted/`, `rejected/`); в образе — `/app/pki` (том) |
| `GATEWAY_OPCUA_CERT_FILE`, `GATEWAY_OPCUA_KEY_FILE` | — | свой сертификат клиента (`.der` или `.pem`) и его закрытый ключ (PEM, PKCS#8), например от УЦ предприятия; задаются вместе. Не заданы — шлюз выпускает самоподписанный в `own/` и `private/` каталога PKI |
| `GATEWAY_OPCUA_APPLICATION_URI` | `urn:scada:gateway` | URI приложения клиента; первым альтернативным именем (SAN) сертификата должен быть он, иначе сервер отвергнет клиента. Проверяется при запуске |
| `GATEWAY_OPCUA_CERT_DAYS` | `1825` | срок самоподписанного сертификата, который шлюз выпускает сам (5 лет; от 1 до 36500). Уже выпущенный сертификат не меняется |
| `GATEWAY_OPCUA_CERT_WARN_DAYS` | `30` | за сколько дней до окончания сертификата предупреждать (журнал, событие `SYSTEM`, метрика `scada_opcua_cert_expiry_days`) |
| `GATEWAY_OPCUA_TRUST_SERVER_CERTS` | `false` | доверять любому сертификату сервера. **Только для стенда**: без проверки сервера защищённый канал не защищает от подмены |

### Команды

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GATEWAY_COMMANDS_MAX_AGE_MS` | `30000` | команда старше не исполняется (`REJECTED_EXPIRED`) |
| `GATEWAY_COMMANDS_GROUP_ID` | `scada-gateway-group` | группа, в которой Kafka хранит позицию чтения топика команд. Позиция — по топику, поэтому станциям со своими топиками команд общая группа не мешает; своя нужна для раздельных ACL. При смене имени шлюз начнёт с конца топика: команды, пришедшие, пока он стоял, не исполнятся |
| `GATEWAY_COMMANDS_VERIFY_MS` | `0` | через сколько мс после записи по OPC UA или PAC перечитать значение; не изменилось — `FAILED_NOT_APPLIED`. `0` — не проверять. У PAC шлюз на это время отпускает соединение (опрос не ждёт) и затем сам запрашивает свежий снимок |

### Аварии ПЛК (ptusa)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GATEWAY_PAC_ALARMS_ENABLED` | `true` | читать аварии у PAC-контроллеров (команда 103 прошивке) и у OPC UA-контроллеров (узел `ns=2;s=SYSTEM.ALARMS` фасада `ptusa-opcua`) и исполнять команды `PAC_ALARM`. `false` — снимков нет, команда `PAC_ALARM` получает `REJECTED_UNKNOWN_TAG` |
| `GATEWAY_PAC_ALARMS_INTERVAL_MS` | `300` | как часто читать список аварий контроллера, независимо от периода опроса тегов (`0` — ошибка запуска: выключают `GATEWAY_PAC_ALARMS_ENABLED`) |

Аварии читаются у каждого включённого PAC- и OPC UA-контроллера, если у него не задано `pacAlarms: false`. У PAC — тем же соединением, что опрос тегов, по
очереди с ним; у OPC UA-сервера без узла `SYSTEM.ALARMS` (не фасад ptusa) их нет — одна строка в журнале. Снимок в Kafka несёт `controllerId` (поле `id` контроллера, не задан — `name`) и `path` — путь
проекта в мониторе (`alarmsPath` контроллера, не задан — общее начало имён его тегов по сегментам через точку; при
запуске шлюз пишет в журнал, что вычислил; совпадение `path` у двух контроллеров — предупреждение: одну прошивку видят
дважды, например PAC напрямую и OPC UA через фасад, — оставьте аварии одному, у другого `pacAlarms: false`). Формат снимка и команды — `docs/MONITOR_INTEGRATION.md`.

## controllers.yaml — станция

Корень — `opcua.servers` (название осталось от Java-шлюза; в списке могут быть контроллеры любого протокола).

```yaml
opcua:
  servers:
    - id: phoenix-001                     # не используется, оставлено для совместимости формата
      name: "Phoenix Contact"             # уникальное имя контроллера
      endpoint: "opc.tcp://${PLC_HOST}:4840"
      security: "Basic256Sha256"          # только OPC UA; по умолчанию None
      username: "gateway"                 # только OPC UA; вместе с password
      password: "${PLC_PASSWORD}"
      enabled: true                       # по умолчанию false!
      tags:
        - name: "Площадка.Станция.Модуль.LINE1V0.ST"   # уникальное имя: ключ Kafka и адрес команды
          nodeId: "ns=2;s=6"                            # адрес в контроллере (уникален в пределах контроллера)
          dataType: INT32
          enabled: true                                 # по умолчанию false!
          pollingRate: 1000
          writable: false
          channelId: 6
          deviceName: LINE1V0
          fieldName: ST
          unit: "°C"
          minValue: 0
          maxValue: 100
          writeMin: 0                                   # пределы значения команды, включительно
          writeMax: 95
          history: {deadband: 0.5, deadbandPercent: 1, minIntervalMs: 60000, maxIntervalMs: 600000}
```

### Контроллер

| Поле | Обязательно | Назначение |
|---|---|---|
| `name` | да | уникальное имя; по нему контроллер связывается с таблицей `controllers` |
| `endpoint` | да | протокол определяется **по началу адреса**: `opc.tcp://host:порт`, `modbus://host:порт` (по умолчанию 502), `pac://host:порт`. Неизвестная схема — ошибка |
| `enabled` | — | **по умолчанию `false`**: выключенный контроллер не опрашивается и не проверяется; из БД не удаляется |
| `security` | — | только OPC UA. `None`; политика `Basic256Sha256`, `Aes128_Sha256_RsaOaep`, `Aes256_Sha256_RsaPss`, `Basic256`, `Basic128Rsa15`; к ней необязательный режим `_Sign` или `_SignAndEncrypt` (по умолчанию `SignAndEncrypt`). Регистр, `_`, `-` и пробелы не важны |
| `acquisition` | `poll` | только OPC UA. `poll` — шлюз каждый цикл читает «созревшие» теги запросом Read; `subscription` — подписки (MonitoredItems), сервер сам присылает изменения — см. «OPC UA: подписки» |
| `username`, `password` | — | только OPC UA, задаются **вместе**. На канале `None` идут открытым текстом (предупреждение) |
| `identity` | — | как опознать контроллер при подключении, см. ниже. Только PAC и OPC UA |
| `id` | — | id контроллера для аварий ПЛК: ключ снимка в `scada.pac-alarms` и `controllerId` команды `PAC_ALARM`; не задан — `name`. На общем Kafka должен быть уникален между станциями |
| `pacAlarms` | `true` | PAC и OPC UA: `false` — аварии ПЛК у контроллера не читаются, команда `PAC_ALARM` к нему — `REJECTED_UNKNOWN_TAG`, прежний снимок удаляется из топика (tombstone). Нужен, если одну прошивку видят два контроллера (по `pac://` и через фасад) |
| `alarmsPath` | — | PAC и OPC UA: путь проекта в мониторе для снимка аварий ПЛК (`path`). Не задан — общее начало имён тегов; если у имён нет общего начала, аварии контроллера не публикуются (предупреждение при запуске) |
| `tags` | — | список тегов |

`security`/`username`/`password` у Modbus и PAC — ошибка запуска: защиты на уровне этих протоколов нет, и делать вид, что
она есть, нельзя.

#### Проверка, что подключились к нужному контроллеру (`identity`)

Перепутанный адрес, заменённый ПЛК, переназначенный IP — и шлюз читал бы чужой контроллер и писал в него команды оператора.
Поэтому контроллер можно «опознавать»: при каждом подключении шлюз сверяет имя, которым контроллер называет себя сам.

```yaml
- name: "Барановичи-1.BN1_MCA1"
  endpoint: "pac://${PAC_HOST}:10000"
  identity: {pacName: "BN1-МСА1"}                     # PAC: PAC_name из ответа GET_INFO_ON_CONNECT
- name: "Барановичи-1.BN1_MCA1 (OPC UA)"
  endpoint: "opc.tcp://${PLC_HOST}:4840"
  identity: {pacName: "BN1-МСА1", nodeId: "ns=2;s=SYSTEM.PAC_NAME"}   # OPC UA: значение узла
  # или: identity: {applicationUri: "urn:savushkin:ptusa-opcua"}      # ApplicationUri сервера
```

| Поле | Протокол | Что сверяется |
|---|---|---|
| `pacName` | PAC | `PAC_name` из handshake. У OPC UA — ожидаемое значение узла `nodeId` (задаются **вместе**) |
| `nodeId` | OPC UA | узел, значение которого — имя контроллера. У OPC UA-фасада `ptusa-opcua` и симулятора — `ns=2;s=SYSTEM.PAC_NAME`; допустим и адрес `nsu=…` |
| `applicationUri` | OPC UA | `ApplicationUri` сервера (первый элемент `Server.ServerArray`) |

Имена сравниваются точно (пробелы по краям не в счёт). **Осторожно с кириллицей:** в `BN1-МСА1` буквы «М», «С», «А» — русские; латинские
`MCA` выглядят так же, но имя не совпадёт. В сообщении о несовпадении оба имени показаны и в экранированном виде
(`\u{41c}\u{421}\u{410}`), чтобы разница была видна.

**Не совпало — что делает шлюз:** закрывает соединение, теги контроллера идут с качеством `BAD`, **ни одна команда в него не
уходит** (`FAILED_*`), контроллер `DOWN`, в `/api/status` → `controllers[].identity` статус `MISMATCH` и причина, в журнале
ошибка и событие `CONTROLLER_IDENTITY_MISMATCH` (не чаще раза в минуту на контроллер). Повтор — по обычному расписанию
подключения: поправили адрес или конфигурацию — связь поднимается сама. Узел, который не удалось прочитать, считается
несовпадением. Без `identity` шлюз работает как раньше и при запуске пишет один раз, каких контроллеров имя не проверяется
(Modbus прибор себя не называет — сверки нет). Пустое поле, `identity` у Modbus, `pacName` без `nodeId` у OPC UA, `nodeId`/`applicationUri` у
PAC — ошибка запуска.

`tools/station_config.sh` с переменной `PAC_NAME` (или `-DpacName`) пишет `identity` в генерируемый файл станции. Имя
контроллера — `PAC_name` его прошивки; его называет технолог.

### Тег

| Поле | Обязательно | Назначение |
|---|---|---|
| `name` | да | полный путь канала: **ключ сообщения Kafka и адрес команды**. Уникален на всю станцию |
| `nodeId` | да | адрес в контроллере: OPC UA — `ns=2;s=6` или `nsu=<URI пространства имён>;s=6` (номер пространства шлюз узнаёт у сервера при подключении: `ns` может смениться с новой версией проекта ПЛК, URI — нет); PAC и Modbus — любой уникальный ключ (в конфигурации станции — `pac:385`, `modbus:40001`). **Уникален в пределах контроллера** — по нему тег связывается со строкой БД |
| `dataType` | да | тип по началу имени: `BOOL…` — логический; `INT…` — целый; `FLOAT…`, `REAL…`, `DOUBLE…` — вещественный; `STRING…` — строка. Тип определяет приведение значения команды и декодирование Modbus. У OPC UA значение пишется в типе **узла** — см. «OPC UA: проверка узлов и типы» |
| `enabled` | — | **по умолчанию `false`**: выключенный тег не опрашивается |
| `pollingRate` | — | период опроса, мс. Период цикла контроллера — **наименьший положительный** `pollingRate` его тегов (не меньше 100 мс; без значений — 1000 мс). Теги с большим значением опрашиваются тем же циклом |
| `writable` | — | можно ли писать командой. Modbus не пишется никогда, независимо от значения |
| `protocol` | — | `opcua` (по умолчанию), `modbus`, `pac`. **Должен совпадать с протоколом контроллера**, иначе ошибка запуска (иначе тег никто не опрашивал бы) |
| `channelId` | — | номер канала в базе монитора (информационно, в БД) |
| `deviceName`, `fieldName` | PAC: да | прибор и поле в снимке PAC (`LINE1V0` / `ST`, `RT_PAR_F[12]`, `PAR_MAIN[1].P_CZAD_S`). Прибор может быть элементом массива: `RECMAN[1]` читается как `t.RECMAN[1]` (менеджер рецептов ptusa). Допустимы буквы, цифры, `_`, `[`, `]`, `.` — значения подставляются в Lua-текст команды. Остальные протоколы — метаданные |
| `deviceType` | — | тип прибора (метаданные, доступны скриптам) |
| `unit` | — | единица измерения |
| `minValue`, `maxValue` | — | пределы для аларма (`GATEWAY_ALARMS_ENABLED=true`) |
| `writeMin`, `writeMax` | — | пределы значения **команды**, включительно; можно задать один. Значение вне них в ПЛК не уходит — `REJECTED_OUT_OF_RANGE`, пределы в `message`. Только у числового тега (`INT…`, `FLOAT…`, `REAL…`, `DOUBLE…`); `writeMin` больше `writeMax`, `.nan`, `.inf` — ошибка запуска. Единицы — как у телеметрии: проверяется значение оператора до скрипта канала `write()`, у целого тега — после отбрасывания дробной части (то, что будет записано). Без пределов значение ограничено только типом |
| `modbusAddress` | Modbus: да | адрес holding-регистра в нотации 4xxxx: от `40001` до `105536` (для 32-битного — до `105535`) |
| `modbusUnitId` | — | Unit ID (по умолчанию 1). **Один на контроллер** — разные значения у тегов одного контроллера не принимаются |
| `modbusType` | — | информационно (в БД); декодирование идёт по `dataType` |
| `history` | — | переопределение фильтра истории тега: `deadband`, `deadbandPercent`, `minIntervalMs`, `maxIntervalMs` |

**Запись в PAC.** Команда строится так, как её разбирает прошивка (`pac/lua.rs::command_text`):

| Тег | Команда |
|---|---|
| `LINE1V0` / `ST` | `__LINE1V0:set_cmd('ST', 1, 1)` |
| `OBJECT1` / `RT_PAR_F[62]` | `__OBJECT1:set_cmd('RT_PAR_F', 62, 7.5)` — индекс отдельным аргументом; `set_cmd('RT_PAR_F[62]', 1, v)` прошивка принимает с кодом 0 и **ничего не меняет** |
| `RECMAN[1]` / `CMD` | `__RECMAN[1]:set_cmd( "CMD", 1, 1001 )` — менеджер рецептов разбирается регулярным выражением: двойные кавычки, пробелы внутри скобок, строка в кавычках, число без знака. Отрицательное число и строка с кавычкой отклоняются (`REJECTED_TYPE_MISMATCH`): прошивка молча проигнорировала бы их |

Modbus-декодирование: `FLOAT` — два регистра (младший первым, как `struct.pack('<f')`); целые — регистр со знаком
(int16); `BOOL` — регистр ≠ 0.

**OPC UA: подписки (`acquisition: subscription`).** Вместо чтения всех узлов каждый цикл шлюз подписывается на них: сервер
сам опрашивает свои узлы с периодом `samplingInterval` и присылает только изменения. Нагрузка на ПЛК и сеть падает с «все теги
каждый цикл» до «только изменившиеся» (замер — `docs/STRESS_TEST.md`).

* **Период.** `samplingInterval` тега — настройка «период» из `channel.tag-settings`, иначе `pollingRate` тега; интервал публикации
  подписки — цикл контроллера (минимальный `pollingRate`). Изменение быстрее `samplingInterval` сервер не видит так же, как опрос не
  видит изменения быстрее своего периода: короткий импульс ловится уменьшением `pollingRate` тега — по сети при этом идут только
  изменения. У каждого узла на сервере очередь из 10 значений: между двумя публикациями изменения не теряются, все доходят до обработки.
  Период тега из `channel.tag-settings`, поменявшийся при работе, подписка применяет при следующем подключении (при опросе — сразу).
* **Обработка та же.** Изменение идёт в обработку сразу, как пришло; раз в цикл контроллера в неё подаются последние известные
  значения «созревших» тегов — полная переотправка, фильтр «по исключению», качество, история и алармы работают как при опросе.
* **Связь.** Признак связи — приходят ли уведомления; если их нет дольше трёх циклов (не меньше 5 с), шлюз читает состояние сервера
  (`ServerStatus.State`): не ответил — `DOWN`, дольше `GATEWAY_STALE_AFTER_MS` — сессия пересоздаётся, подписки создаются заново на новой
  сессии. Закрыл подписку сам сервер — пересоздание сразу. «Все узлы `BAD`» — по-прежнему обрыв.
* **Запись.** Сразу после записи шлюз читает все узлы запросом (как опрос после записи), не дожидаясь уведомлений.
* **Пределы сервера.** Размер подписки и запроса берётся из `MaxMonitoredItemsPerSubscription` и `MaxMonitoredItemsPerCall`; сервер, не
  назвавший предел и ответивший `BadTooManyMonitoredItems`, получает запрос вдвое меньше, а полная подписка закрывается и открывается
  следующая (у async-opcua это 1000 узлов). Узлы, которые сервер отказался взять, идут `BAD`.
* **Если подписки не создались** (сервер их не поддерживает, лимит числа подписок) — это сеанс идёт обычным опросом, а не обрывом:
  предупреждение в журнале и событие `CONFIG`; при следующем подключении шлюз пробует снова.
* **Резерв.** Оба экземпляра пары подписываются (как оба опрашивают): активность определяет `Processor`, а резервный при смене роли
  уже имеет свежие значения. Нагрузка на сервер — две подписки вместо двух полных опросов.
* **Выбор режима.** Подписки выгодны на ПЛК со встроенным OPC UA-сервером и большим числом тегов; для сервера, который подписки
  реализует плохо (проверьте на стенде), оставьте `poll`. Опрос после обрыва и проверка узлов (`prepare`) работают в обоих режимах.

**OPC UA: проверка узлов и типы.** При каждом подключении шлюз читает у сервера таблицу пространств имён, предел
`MaxNodesPerRead` и у узла каждого включённого тега — атрибуты `DataType` и `ValueRank`. Найденное — сводкой в журнале
(повторно — только если изменилось), событием `CONFIG` (`WARNING`) и в `/api/status` (поле `opcua` у контроллера).
Запуск и опрос это не останавливает: проблемный тег идёт `BAD`, остальные работают.

| Что найдено | Что делает шлюз |
|---|---|
| адрес не разбирается (опечатка, `nsu=` с URI, которого у сервера нет) | тег не читается и сразу `BAD`; команда — `REJECTED_UNKNOWN_TAG` |
| узла нет на сервере (`BadNodeIdUnknown`) | тег `BAD` |
| узел не переменная, массив или типа `DateTime`, `Guid`, `ByteString`, `LocalizedText`, структура… | тег `BAD`: такие значения шлюз не передаёт; запись отклоняется |
| `dataType` тега по смыслу не совпадает с типом узла (`FLOAT` на узле `Int32`) | предупреждение; значения читаются и пишутся в типе узла |
| сервер принимает меньше 500 узлов в одном запросе | шлюз читает пачками по пределу сервера (и уменьшает пачку сам, если сервер ответил `BadTooManyOperations`) |
| сервер не ответил на чтение атрибутов (старый или урезанный сервер) | предупреждение; опрос как раньше, запись — по `dataType` тега |

Сервер OPC UA проверяет тип записываемого значения строго: `Int16` в узел `Int32` он отклонит (`BadTypeMismatch`), хотя
число то же. Поэтому значение команды шлюз приводит к типу узла:

| Тип узла (`DataType`) | Значение команды |
|---|---|
| `Boolean` | `true`/`false`; число ≠ 0 — `true` |
| `SByte`, `Byte`, `Int16`, `UInt16`, `Int32`, `UInt32`, `Int64`, `UInt64` (и `IntegerId`, `Counter`) | целое; дробная часть отбрасывается; вне диапазона типа — `REJECTED_TYPE_MISMATCH` (300 в `Byte` не превратится в 44) |
| `Float`, `Double` (и `Duration`) | число; вне диапазона `Float` — `REJECTED_TYPE_MISMATCH` |
| `String` (и `LocaleId`, `NumericRange`) | строка |
| тип неизвестен (сервер не сообщил, нестандартный тип) | по `dataType` тега, как раньше |

Пример предупреждения в журнале:

```text
⚠ Барановичи-1.BN1_MCA1: dataType тегов не совпадает с типом узлов, значения идут в типе узла (2): LINE1.V1.ST (ns=2;s=17): dataType FLOAT, узел Int32; …
```

### Подстановка `${…}`

`${ИМЯ:значение}` — значение из окружения или указанное по умолчанию (пустое `${ИМЯ:}` допустимо); `${ИМЯ}` без
умолчания **обязательна** — без неё запуск не пройдёт, а не подставится пустая строка. Подстановка текстовая и идёт до
разбора YAML: пароль со спецсимволами (`#`, `:`, кавычки) берите в кавычки (`password: "${PLC_PASSWORD}"`).

## scripts.yaml — пользовательские скрипты

Лежит в `GATEWAY_SCRIPTS_DIR` вместе с `.lua`-файлами. Полное описание контракта скрипта — в шапке
`config/scripts/scripts.yaml`, примеры — `sensor_break.lua`, `scale.lua`, `deadband.lua` там же.

```yaml
scripts:
  - script: scale.lua                    # файл в этой папке (вне папки — ошибка)
    tags: ["*.M_P_ON_TIME.LINE?M*.P_ON_TIME"]   # маски имён тегов: * — любые символы, ? — один, остальное буквально
    params: {k: 0.001, b: 0}             # доступны скрипту как ctx.params
    enabled: true                        # false — привязка временно выключена
```

* `process(value, quality, ctx)` вызывается на **каждое** снятое значение до фильтра публикации, алармов и истории;
  возвращает значение и (необязательно) качество `"GOOD"`/`"BAD"`. У кадра BAD `value = nil`.
* `write(value, ctx)` (необязательно) пересчитывает значение команды оператора в значение для ПЛК; цепочка идёт в
  обратном порядке.
* `ctx`: `tag`, `device`, `field`, `device_type`, `data_type`, `unit`, `params`, `timestamp` (мс), `state` — таблица
  канала, живёт между вызовами.
* Несколько привязок на канал — цепочка в порядке файла. Ошибка или превышение времени — кадр `BAD`; после трёх
  превышений подряд скрипт отключается на 30 с.
* Изменения папки подхватываются без перезапуска; версия с ошибкой не применяется (работает прежняя, событие `SCRIPT`).
  Ошибка в скриптах при запуске — отказ запуска. Состояние — `GET /api/scripts`.

## Что проверяется при запуске

Шлюз отказывается стартовать (и пишет, что исправить), если:

* не задана обязательная `${ПЕРЕМЕННАЯ}` или не читается `controllers.yaml`;
* имена контроллеров или включённых тегов повторяются или пусты;
* схема `endpoint` неизвестна;
* `security` не разбирается; `username` без `password` и наоборот; защита задана у Modbus или PAC;
* `identity` пуст, не подходит протоколу контроллера (см. «Проверка, что подключились к нужному контроллеру»);
* протокол тега не совпадает с протоколом контроллера;
* `nodeId` повторяется в пределах контроллера;
* у PAC-тега нет `deviceName`/`fieldName` или в них недопустимые символы;
* у Modbus-тега нет `modbusAddress`, он вне 40001…105536 или `modbusUnitId` у тегов контроллера разные;
* неверное число, время или режим в любой переменной окружения, неверный `sslmode`; `GATEWAY_PAC_ALARMS_INTERVAL_MS=0`;
* `GATEWAY_HA_ENABLED=true` при выключенной Kafka;
* у контроллеров OPC UA задан свой сертификат (`GATEWAY_OPCUA_CERT_FILE`) или есть защищённый канал, а сертификат
  клиента не читается, ключ не от него или URI приложения не совпадает с сертификатом;
* ошибка в `scripts.yaml` или `.lua` при первой загрузке;
* HTTP-порт занят.

## Настройки тегов из `channel`

Наладчик правит в мониторе (узел `channel`) период опроса и зону нечувствительности канала; `channel` публикует их в сжатый топик
`channel.tag-settings` (ключ — имя тега, значение — JSON, `null` — настройки сняты), а шлюз читает топик целиком с начала и применяет записи на лету,
без перезапуска. Контракт — `2026-10-19-tag-settings-contract.md` бэкенда.

| Поле записи | Что делает шлюз |
|---|---|
| `poll.mode = "period"`, `poll.periodMs` | тег читается не чаще раза в `periodMs` (тег с периодом 3 с при цикле контроллера 1 с — каждый третий цикл; чаще цикла не бывает). Цикл контроллера по-прежнему определяют `pollingRate` из YAML. У OPC UA читаются только «созревшие» узлы; у PAC снимок читается целиком, а в Kafka идут только созревшие теги; у Modbus блоки читаются целиком, в обработку идут созревшие теги |
| `poll.mode = "cycle"` | значение из YAML не меняется («каждый цикл» и есть базовый период) |
| `deadband` | зона нечувствительности **локальной истории** тега (подменяет `history.deadband` из YAML; `0` — любое изменение значимо). Фильтр публикации в Kafka общий и остаётся прежним |
| `log` | шлюзу не нужен: архив ведёт `runtime` |

Тег без записи работает по YAML; tombstone возвращает тег к YAML и опрос не выключает — состав тегов по-прежнему решает YAML. Если топика ещё нет
(его создаёт `channel`), шлюз пишет предупреждение, повторяет попытку раз в 10 с и работает по YAML. Оба экземпляра пары резервирования читают топик
сами (группа не используется). В метрике `scada_tag_settings_tags` — число тегов с применёнными настройками; в журнале при запуске — «Настройки тегов: прочитано N записей…».
