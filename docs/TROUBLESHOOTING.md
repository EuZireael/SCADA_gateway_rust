## Шлюз не запускается

Шлюз сразу завершается с кодом ≠ 0 и **текстом причины в журнале**: конфигурацию, которую нельзя применить, он не
принимает (`docs/CONFIGURATION.md#что-проверяется-при-запуске`).

| Сообщение (начало) | Причина | Что делать |
|---|---|---|
| `задайте переменные окружения: PLC_HOST…` | в `controllers.yaml` есть `${ПЕРЕМЕННАЯ}` без значения по умолчанию | задать переменную или написать `${ПЕРЕМЕННАЯ:значение}` |
| `не прочитан …/controllers.yaml` | неверный путь, том не смонтирован | проверить `CONTROLLERS_YAML` и монтирование (`/app/config/controllers.yaml`) |
| `controllers.yaml не разобран` | ошибка YAML или неизвестный тип поля | смотреть строку и столбец в сообщении; пароль со спецсимволами брать в кавычки |
| `конфигурация контроллеров не принята:` и список | дубли имён, протокол тега не совпадает с контроллером, повтор `nodeId`, нет `modbusAddress`, адрес вне диапазона, недопустимые символы в адресе PAC | исправить пункты списка по порядку |
| `security: "…" — ожидается None или политика` | опечатка в `security` | допустимые значения — `docs/CONFIGURATION.md` |
| `security/username/password поддерживаются только для OPC UA` | защита задана у Modbus или PAC | убрать: защиты на уровне этих протоколов нет |
| `username и password задаются вместе` | указан только один из них | задать оба или ни одного |
| `sslmode="…": допустимо disable, allow, prefer, require, verify-ca, verify-full` | неверный режим TLS БД | исправить `DB_SSLMODE` или `?sslmode=` |
| `БД недоступна` / `миграция схемы` | неверный пароль, непроверяемый сертификат, нет прав на схему | см. текст ниже строки; сетевой сбой запуск не останавливает — см. раздел «База данных и REST» |
| `горячее резервирование … включите KAFKA_ENABLED` | `GATEWAY_HA_ENABLED=true` при `KAFKA_ENABLED=false` | пара работает только через Kafka |
| `HTTP-порт занят` | порт `SERVER_PORT` (8888) уже слушает другой процесс | сменить порт или остановить старый шлюз |
| `не создан Kafka-продюсер` | неизвестное или неверное свойство в `KAFKA_CLIENT_*` / SASL | проверить имя свойства librdkafka |
| `Пользовательские скрипты …` / `{файл}: нет функции process` | ошибка в Lua или `scripts.yaml` при первой загрузке | исправить скрипт; при перезагрузке на ходу ошибка не фатальна — остаётся старая версия |
| `ИМЯ_ПЕРЕМЕННОЙ=значение: …` | неверное число или время в переменной окружения | в сообщении указано имя переменной |

## Нет связи с контроллером

Признаки: `scada_controllers_connected` меньше `scada_controllers_total`, в `/actuator/health` контроллер `DOWN`, события
`CONNECTION` (`CONNECT_FAILED`, «Потеряна связь»), по тегам идут кадры `BAD`.

| Симптом | Причина | Что делать |
|---|---|---|
| OPC UA: `нет конечной точки …/… или к ней не подключиться` | политика или режим `security:` не поддерживаются сервером | проверить, какие политики включены у ПЛК; `None` для проверки |
| OPC UA: сертификат сервера не принят, файл в `rejected/` | сервер не в `trusted/` | **перенести** (не копировать) файл из `…/pki/rejected/` в `…/pki/trusted/`; сертификат шлюза (`own/cert.der`) — в доверенные на стороне ПЛК |
| OPC UA: пароль неверен | `username`/`password` | журнал содержит причину, но не пароль |
| OPC UA: подключается к `::1` и не может | `localhost` → IPv6, сервер слушает только IPv4 | шлюз пробует все адреса имени сам; для надёжности пишите `127.0.0.1` |
| OPC UA: `все N узлов вернули BAD` | сервер жив, но данных за ним нет (отвалилась шина или рантайм ПЛК) | это обрыв; смотреть ПЛК или фасад `ptusa-opcua` |
| Modbus: `исключение Modbus … на всех блоках` | контроллер отвечает, но регистров нет (шлюз Modbus TCP→RTU без связи с прибором) или неверный `modbusUnitId` | проверить unit id и адреса |
| Modbus: часть тегов `BAD`, остальные `GOOD` | регистра нет в карте ПЛК (исключение на одиночном теге) | исправить `modbusAddress` или выключить тег |
| PAC: `нет приветствия 'PAC accept'` | на порту не PAC | проверить адрес и порт |
| PAC: `таймаут чтения` сразу после подключения | прошивка рвёт соединение, если клиент молчит дольше ~300 мс | шлюз шлёт первый запрос сразу; проверить сеть и нагрузку на ПЛК |
| PAC: `рассинхрон пакета`, `ошибка zlib` | другая версия протокола или мусор в канале | в журнале версия протокола (ожидается 104); соединение пересоздаётся само |
| PAC: все теги прибора вида `RECMAN[n]` `BAD` | менеджер рецептов лежит в снимке массивом `t.RECMAN[n]`; шлюз читает `deviceName: "RECMAN[1]"` именно так | проверить, что в снимке есть `t.RECMAN` (`simulator probe-pac host порт`) и номер элемента |
| PAC: запись в поле-массив (`RT_PAR_F[12]`) даёт `APPLIED`, а значение не меняется | раньше шлюз слал индекс внутри имени поля, и прошивка принимала команду с кодом 0, ничего не меняя | исправлено: индекс идёт отдельным аргументом; если встретите у другой версии — обновите шлюз |
| PAC: порт 10000 занят (на хосте настоящий `ptusa_main`) | симулятор не поднимается на занятом порту | `PAC_PORT` симулятору и `SIM_PAC_PORT` шлюзу и тестам, либо `SIM_PAC_PORT` для compose |
| Контроллер `UP`, но часть тегов `BAD` | у PAC — нет прибора или поля в снимке; у OPC UA — узел с плохим статусом или из списков ниже | сверить `deviceName`/`fieldName`/`nodeId`; `simulator probe-pac host порт` печатает снимок прошивки; у OPC UA — `/api/status`, поле `opcua` контроллера |

### OPC UA: проверка узлов при подключении

После каждого подключения шлюз проверяет узлы тегов (`docs/CONFIGURATION.md`, «OPC UA: проверка узлов и типы»). Сводка —
в журнале (`⚠ <контроллер>: …`, повторно — только если изменилась), в событии `CONFIG` и в `/api/status` → `controllers[].opcua`:
`unresolved`, `unknownNodes`, `unsupportedNodes`, `typeMismatch` (`count` и первые 50 тегов), `maxNodesPerRead`, `readChunk`.

| Сообщение | Причина | Что делать |
|---|---|---|
| `адрес узла не разобран, теги не читаются` | опечатка в `nodeId` или `nsu=` с URI, которого нет в таблице пространств имён сервера | исправить адрес; URI пространств сервера видны в любом клиенте OPC UA (`Server` → `NamespaceArray`) |
| `узлов нет на сервере, теги будут BAD` | `nodeId` не совпадает с проектом ПЛК: опечатка, узел удалён или переименован, сменился номер `ns` с новой версией проекта | сверить адреса с проектом ПЛК; если «уехал» номер пространства — перейти на `nsu=<URI>;…` |
| `значения узлов шлюз не передаёт, теги будут BAD` | узел — массив, не переменная (папка, объект) или типа `DateTime`, `Guid`, `ByteString`, структура | указать скалярную переменную (элемент массива — отдельным узлом в проекте ПЛК) или выключить тег |
| `dataType тегов не совпадает с типом узлов, значения идут в типе узла` | `dataType` в YAML по смыслу другой (`FLOAT` на узле `Int32`) | на работу не влияет: чтение и запись идут в типе узла; исправить `dataType`, чтобы правила зоны нечувствительности и скрипты видели верный тип |
| `сервер принимает до N узлов в запросе — читаю пачками по N` (INFO) | у сервера предел `MaxNodesPerRead` меньше 500 | ничего: цикл опроса делает больше запросов; если растёт `scada_poll_overruns_total` — увеличить `pollingRate` |
| `сервер не принимает N узлов в одном запросе — читаю по M` | сервер ответил `BadTooManyOperations`, а предел не объявил | ничего: шлюз уменьшил пачку сам до конца сессии |
| `типы узлов не прочитаны (…) — запись по dataType тегов` | сервер не ответил на чтение атрибутов узлов (`/api/status`: `typesUnknown: true`) | опрос идёт как раньше, запись — по `dataType` тега; проверить версию сервера |
| `сведения о сервере не прочитаны (…) — пачки по 500` | сервер не отдал `NamespaceArray` и `MaxNodesPerRead` | опрос идёт; адреса `nsu=` не разберутся — писать `ns=` |

## В Kafka нет данных или их мало

| Симптом | Причина | Что делать |
|---|---|---|
| Ничего не приходит, `/actuator/health`: `kafka DOWN` | брокер недоступен, неверный адрес, нет прав | `SPRING_KAFKA_BOOTSTRAP_SERVERS`, сеть, SASL/TLS; `scada_kafka_send_errors_total` растёт |
| Сообщения идут редко | **это норма**: публикация «по исключению» — тег уходит при изменении и раз в `GATEWAY_PUBLISH_FULL_RESEND_MS` (30 с) | для проверки — `GATEWAY_PUBLISH_ENABLED=false` (каждый цикл) |
| Экземпляр в паре молчит | это резерв | `GET /api/ha`: `role` и `since`; метрика `scada_ha_active` |
| После падения Kafka данные идут, а у монитора старые значения | пока доставка не восстановилась, сообщения теряются (30 с) | после восстановления шлюз сам отправляет все теги заново: `scada_kafka_resyncs_total` вырос? |
| Топики не создаются | у шлюза нет прав на создание или брокер без `auto.create` | создать топики заранее (телеметрия — 3 партиции, алармы — 2, остальные — 1) |
| Монитор считает тег «замолчавшим» | `runtime.telemetry.max-silence-ms` монитора ≤ `full-resend-ms` | сделать `max-silence-ms` больше `GATEWAY_PUBLISH_FULL_RESEND_MS` |
| Кадров `BAD` нет при обрыве | `GATEWAY_SEND_BAD_FRAMES=false` | включить (по умолчанию `true`) |

## Команды

Статус приходит в `scada-command-results`; он же в `event_log` (тип `COMMAND`) и метрике `scada_commands_total{status}`.

| Статус | Значение | Что делать |
|---|---|---|
| `APPLIED` | ПЛК принял запись (для PAC — код 0) | если значение «не меняется»: программа ПЛК может игнорировать запись, `docs/FIRMWARE_WRITE_BEHAVIOR.md`; включите `GATEWAY_COMMANDS_VERIFY_MS` (OPC UA и PAC) |
| `FAILED_NOT_APPLIED` | ПЛК принял, но значение не изменилось | программа не разрешает действие (например, клапан не в ручном режиме) |
| `REJECTED_UNKNOWN_TAG` | тега нет или он выключен; у PAC-тега нет `deviceName`/`fieldName`; у OPC UA-тега не разобран `nodeId` («Адрес узла не разобран») | проверить имя в `tagName` (оно должно совпасть с `name` в YAML посимвольно); адрес — см. «OPC UA: проверка узлов при подключении» |
| `REJECTED_NOT_WRITABLE` | `writable: false` или контроллер Modbus | Modbus не пишется никогда; для остальных — `writable: true` и перезапуск |
| `REJECTED_TYPE_MISMATCH` | значение не приводится к типу тега (в том числе `NaN`, `inf`), скрипт `write` упал, PAC получил строку; у OPC UA — к типу узла: вне диапазона (`300 вне диапазона Byte (0…255)`), узел — массив или неподдерживаемого типа | исправить значение |
| `REJECTED_EXPIRED` | команда старше `GATEWAY_COMMANDS_MAX_AGE_MS` | шлюзы стояли или часы монитора расходятся с брокером (нужен NTP) |
| `FAILED_NO_CONNECTION` | контроллер не подключён | см. «Нет связи с контроллером» |
| `FAILED_WRITE` | сервер отклонил запись или сбой связи | подробности в `message` и журнале |
| монитор: `NO_CONFIRMATION` | шлюз не ответил за таймаут монитора: команда потеряна, повтор отброшен или шлюз был резервом | результат **неизвестен**; проверить значение, повторить осознанно |
| команда «пропала» без статуса | повтор `commandId` за 60 с отбрасывается; нечитаемое сообщение пишется в журнал и пропускается | искать в журнале «Команда … уже обработана» или «Команда не разобрана» |

## Горячее резервирование

| Симптом | Причина | Что делать |
|---|---|---|
| Оба экземпляра резервные | не получают партицию выборов: брокер недоступен, не совпадает `GATEWAY_HA_GROUP_ID`, `session.timeout.ms` вне пределов брокера | журнал `Выборы активного экземпляра прерваны`: брокеру нужен `group.min.session.timeout.ms` ≤ `GATEWAY_HA_SESSION_TIMEOUT_MS` |
| Роль переключается туда-сюда | сеть нестабильна или `session-timeout` слишком мал | увеличить `GATEWAY_HA_SESSION_TIMEOUT_MS` |
| Активный отдал роль без видимой причины | «слепой»: связь потеряна со всеми контроллерами дольше `GATEWAY_HA_YIELD_AFTER_MS`, а партнёр в группе есть | это штатно, события `HA`; чинить связь с ПЛК у этого экземпляра |
| После переключения у монитора пропуск | нет | новый активный сразу шлёт все теги; если пропуск есть — смотреть `scada_kafka_resyncs_total` |
| Команда ушла «не туда» | нет | команды принимает только активный; позиция в топике общая |

## База данных и REST

| Симптом | Причина | Что делать |
|---|---|---|
| `db: DOWN` в health, шлюз работает | БД недоступна | это штатно: телеметрия и команды не страдают, события и история теряются со счётчиком `scada_db_rows_lost_total`; шлюз подключится сам |
| В журнале `БД … недоступна при запуске — шлюз запускается без неё` | БД не ответила за 10 с при запуске | шлюз готовит БД в фоне раз в 5 с; когда получится — событие `SYSTEM` «БД подключена через N с после запуска». До этого команды по `tagId` получают `REJECTED_UNKNOWN_TAG` (по имени — работают), история не пишется |
| `БД всё ещё не подготовлена` раз в 5 минут | БД так и не доступна, или после запуска сменили пароль, или миграция не проходит | текст ошибки — в той же строке; шлюз продолжает работать и пробовать |
| `/api/*` отвечает `401` | задан `GATEWAY_API_TOKEN` | заголовок `Authorization: Bearer <токен>` |
| `/api/events*` отвечает `503` | БД отключена (`DB_ENABLED=false`) | включить БД; `/api/status`, `/api/ha`, `/api/scripts` от неё не зависят |
| `404` на квитирование | такого аларма нет (подтверждаются только события типа `ALARM`) | проверить `id` по `/api/events/alarms` |
| `400` на квитирование | пустой `userId` или длиннее 255 символов | исправить запрос |
| `500` с текстом «ошибка БД» | БД недоступна или запрос не удался; подробности клиенту не отдаются | смотреть журнал шлюза |
| История не пишется | `GATEWAY_PERSIST_TELEMETRY=false` (по умолчанию) | включить; фильтр истории — `GATEWAY_HISTORY_*` |
| Теги без `id` (`tag.id = 0`) | БД выключена | команды работают только по имени тега |

## Скрипты

| Симптом | Причина | Что делать |
|---|---|---|
| Канал стал `BAD` после включения скрипта | ошибка скрипта на значении или превышение времени | `GET /api/scripts`: `lastError`, `errors`; событие `SCRIPT` |
| Ошибка «скрипт приостановлен после 3 превышений времени подряд» | скрипт зависает или слишком медленный | упростить скрипт, проверить `GATEWAY_SCRIPTS_TIMEOUT_MS`; через 30 с пробный вызов |
| Правка скрипта не действует | в новой версии ошибка: работает прежняя | `GET /api/scripts` → `lastReloadError`, журнал |
| «ни к одному каналу не привязан» | маска не совпала с именами тегов | `*` — любые символы, `?` — один; `[`/`]` — буквально |
| `load`, `pcall`, `io` недоступны | так задумано: песочница | задача решается арифметикой и условиями |

## Производительность

| Симптом | Причина | Что делать |
|---|---|---|
| `scada_poll_overruns_total` растёт | цикл опроса не укладывается в период | увеличить `pollingRate`, уменьшить число тегов на контроллер, проверить сеть и время ответа ПЛК (`scada_poll_seconds`) |
| Много памяти | много тегов (≈ 1,7 КБ на тег), история | `GATEWAY_PERSIST_TELEMETRY=false`; замеры — `docs/TELEMETRY_BY_EXCEPTION.md` |
| Процессор растёт | отправка каждого цикла | не отключайте `GATEWAY_PUBLISH_ENABLED`; зоны нечувствительности `GATEWAY_PUBLISH_DEADBAND*` |
| `scada_events_dropped_total` растёт | очередь событий переполнена (буря событий) | искать источник бури: чаще всего флаппинг связи |

## Быстрые проверки

```bash
curl -s localhost:8888/actuator/health | jq              # db, kafka, controllers: UP/DOWN
curl -s localhost:8888/actuator/prometheus | grep ^scada_ # метрики шлюза
curl -s -H "Authorization: Bearer $TOKEN" localhost:8888/api/status | jq   # контроллеры и число тегов
curl -s -H "Authorization: Bearer $TOKEN" localhost:8888/api/ha | jq       # роль в паре
curl -s -H "Authorization: Bearer $TOKEN" localhost:8888/api/scripts | jq  # скрипты и их ошибки
curl -s -H "Authorization: Bearer $TOKEN" "localhost:8888/api/events/severity/ERROR?limit=20" | jq
simulator probe-pac host 10000       # handshake, объектная модель и снимок любого PAC
docker compose logs --tail=100 gateway
RUST_LOG=scada_gateway=debug …       # подробный журнал
```

Если ничего из этого не помогло, приложите к обращению: версию шлюза (первая строка журнала), `GET /actuator/health`,
вывод `GET /api/status`, последние строки журнала и фрагмент `controllers.yaml` без паролей.
