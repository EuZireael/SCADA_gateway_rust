# ptusa-opcua — OPC UA-фасад эмулятора мойки

Отдаёт по OPC UA **все** каналы станции BN1-МСА1 из настоящей прошивки ptusa. Собственный
OPC UA-сервер прошивки (`--opc r|rw`) публикует только `<прибор>.state/.value` — 22 % каналов и
запись, которая на прибор не действует, — поэтому фасад берёт у прошивки весь снимок её родным
протоколом (driver-master) и превращает в узлы OPC UA. Rust (async-opcua + mlua), отдельный пакет
со своим `Cargo.lock`; описание — в документации `src/lib.rs`.

```
прошивка ptusa  ←driver-master→  ptusa-opcua  ←OPC UA :4840→  шлюз
```

- Узел: `ns=2;s=<прибор>.<поле>` (`LINE1V0.ST`, `OBJECT1.RT_PAR_F[12]`, `SYSTEM.UP_TIME`); тип —
  `dataType` канала из конфигурации станции (`config/stations/*.yaml`), запись — `writable`.
- Чтение — снимок раз в `POLL_MS`; исполняется настоящим Lua 5.1 **в песочнице** (снимок присылает
  «прошивка», то есть любой, кто ответит на порту PAC): без `os`/`io`/`load`/байткода, потолок памяти
  64 МБ и 1 с на разбор, распаковка zlib не больше 8 МБ. Нет значения в снимке — `BadNoData`.
- Запись = `__<прибор>:set_cmd('<поле>', <индекс>, v)` ДО сохранения значения; код результата
  прошивки → статус записи (0 — `Good`, иначе `BadInvalidState`). Строка или не число —
  `BadTypeMismatch`.
- Нет связи с прошивкой → все узлы `BadCommunicationError` (сам сервер жив), фасад переподключается
  сам (пауза 1 → 10 с).
- Аварии прошивки — список (команда 103) в узле `SYSTEM.ALARMS`, действие над аварией — метод
  `SYSTEM.ALARM_CMD` (команда 104), см. «Аварии прошивки» ниже.

Стенд целиком — `docker-compose.moika.yml` в корне репозитория. Запуск без Docker:

```sh
cd ptusa-opcua && cargo build --release
PAC_HOST=127.0.0.1 PAC_PORT=10100 STATION_CONFIG=../config/stations/BN1_MCA1.yaml \
  OPCUA_BIND='[::]:4840' ./target/release/ptusa-opcua
```

`OPCUA_BIND='[::]:4840'` — двойной стек (IPv4 и IPv6): нужен сторонним клиентам OPC UA, которые берут
первый адрес из DNS (`localhost` → `::1`) и не пробуют остальные. Шлюз так не страдает: он сам выбирает
доступный адрес имени, поэтому `PLC_HOST=localhost` работает и с `0.0.0.0:4840`. В контейнере IPv6 может
быть выключен — там `0.0.0.0:4840`, а порт пробрасывает Docker.

Настройки: `PAC_HOST`/`PAC_PORT` (прошивка), `PAC_NAME` (имя прошивки, `PAC_name`: задано — фасад не открывает соединение с прошивкой,
назвавшей себя иначе, значений чужой станции не отдаёт, и команды в неё не идут), `STATION_CONFIG`, `OPCUA_BIND` (на чём слушать),
`OPCUA_ENDPOINT` (адрес в ответе FindServers; конечные точки GetEndpoints строятся из адреса
привязки — async-opcua не разделяет эти два адреса, шлюз подключается по адресу из своего конфига
и анонс не использует), `POLL_MS` (период снимка, 500), `ALARMS_POLL_MS` (период чтения аварий, 300), `RUST_LOG`. `ptusa-opcua healthcheck` —
проверка для контейнера: порт OPC UA открыт и прошивка отвечает (с `PAC_NAME` — своё имя).

## Защита

Фасад отдаёт значения станции и принимает команды в прошивку, поэтому **без настроек защиты он не стартует**: анонимный вход и
канал без защиты включаются только явно.

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `OPCUA_SECURITY` | `Basic256Sha256_SignAndEncrypt` | политики через запятую: `None`, `Basic256Sha256`, `Aes128_Sha256_RsaOaep`, `Aes256_Sha256_RsaPss`, к ним `_Sign` или `_SignAndEncrypt` (как `security:` шлюза) |
| `OPCUA_USERS_FILE` | — | файл пользователей: строки `имя хеш-argon2 роль` (`#` — комментарий, роль `read` или `write`) |
| `OPCUA_ALLOW_ANONYMOUS` | `false` | пускать без пароля — только стенд |
| `OPCUA_PKI_DIR` | `/var/lib/ptusa-opcua/pki` | сертификат сервера и доверенные клиенты; **каталог постоянный** (в образе — том) |
| `OPCUA_TRUST_ALL_CLIENTS` | `false` | доверять любому сертификату клиента — только стенд |
| `OPCUA_CERT_DAYS` | `3650` | срок сертификата сервера, выпускаемого при первом запуске |
| `OPCUA_CERT_HOSTS` | — | имена и адреса в сертификате сервера через запятую (хост из `OPCUA_ENDPOINT` добавляется сам) |

Порядок настройки:

1. Хеш пароля: `echo 'пароль' | ptusa-opcua hash-password` (в образе: `docker run --rm -i ptusa-opcua hash-password`). Пароль в файле не
   хранится; строку `имя хеш роль` положите в файл, который монтируется в контейнер только на чтение (`OPCUA_USERS_FILE`).
2. Роли: `write` — чтение, запись и действия над авариями (команды в прошивку); `read` — чтение, запись и вызов `SYSTEM.ALARM_CMD`
   получают `BadUserAccessDenied`. Шлюзу, который пишет команды монитора, нужен пользователь с `write`.
3. Пароль уходит только по защищённому каналу: точка `None` не принимает пользователей с паролем (а `None` вместе с пользователями без
   анонимного входа — ошибка запуска).
4. Клиенты: сертификат клиента (шлюза) при первом подключении попадает в `pki/rejected/`; переложите его в `pki/trusted/`
   (имя файла не меняйте) — следующая попытка пройдёт. Так доверие выдаёт администратор, а не любой, кто достучится до порта.
5. Сертификат сервера выпускается при первом запуске на `OPCUA_CERT_DAYS` дней в `pki/own/cert.der` (+ `pki/private/private.pem`) и
   потом не меняется, пока каталог сохранён. Срок виден в журнале при запуске; за 30 дней до конца фасад предупреждает. Перевыпуск:
   остановить фасад, удалить `own/cert.der` и `private/private.pem`, запустить — новый сертификат надо снова внести в доверенные
   у клиентов (на шлюзе: `GATEWAY_OPCUA_PKI_DIR/trusted/`).
6. Порт PAC прошивки (10000) закройте сетевым ограничением: к нему должен доходить только фасад. Без этого защита фасада обходится
   (`docs/OPERATIONS.md`, чек-лист).

Что видно в журнале фасада: `🔓 вход <имя> (роль …)`, `🚫 вход отклонён` (неверный пароль, неизвестный пользователь, анонимный вход без
разрешения), предупреждения `⚠` при запуске — анонимный вход разрешён, точка без защиты, доверие любым клиентам. Отдельной записи об
отклонённой записи роли `read` в журнале нет: клиент получает `BadUserAccessDenied`, а сервер выбирает отказ до обработчика записи.

Стенд репозитория (`docker-compose.moika.yml`) включает открытый режим явно — `OPCUA_SECURITY=None`, `OPCUA_ALLOW_ANONYMOUS=true`,
`OPCUA_TRUST_ALL_CLIENTS=true`: так шлюз стенда подключается без пароля и сертификатов. Для боевого запуска эти три строки не нужны.

Служебные узлы: `ns=2;s=SYSTEM.PAC_NAME` — имя, которым прошивка назвала себя (по нему шлюз сверяет контроллер: `identity.nodeId`),
`ns=2;s=SYSTEM.LINK_OK` — есть ли связь с прошивкой.

## Аварии прошивки

Список аварий прошивка отдаёт командой 103 — фасад читает его раз в `ALARMS_POLL_MS` по своему соединению (сбой или долгий разбор
списка не задерживают снимок) и исполняет ответ в песочнице, в отдельном от снимка стейте. Разбор ответа, формат JSON и строка
команды 104 — общий со шлюзом крейт `ptusa-alarms/` (шлюз шлёт 103/104 сам у `pac://`-контроллеров). Узел
`ns=2;s=SYSTEM.ALARMS` (String) — JSON-список; значение меняется только вместе со списком:

```json
{"id": 87, "alarms": [{"objectType": 102, "objectNumber": 2, "alarmNumber": 1, "critical": false,
  "description": "'Танк 2' - не включена операция 1 'Мойка' - нет сигнала 'MCA4LINE1DI1 (Линия свободна)'.",
  "group": "ответ", "priority": 750, "state": "ALARM", "suppressed": false}]}
```

| Поле | Что это |
|---|---|
| `id` | счётчик изменений списка у прошивки |
| `objectType` | тип объекта (`id_type`): у объектов ptusa ≥ 100 (танк — 102), у устройств — тип устройства; у критических `null` |
| `objectNumber` | номер объекта, серийный номер устройства или параметр критической ошибки (`id_n`) |
| `alarmNumber` | номер сообщения внутри объекта (`id_object_alarm_number`; у устройств отрицательный); у критических `null` |
| `critical` | критическая ошибка прошивки (командой не квитируется) |
| `description`, `group`, `priority` | текст для оператора, группа (`тревога`, `сообщение`, `ответ`), приоритет (100 — ошибка связи, 250 — тревога, 500 — сообщение, 750 — ответ, 1000 — напоминание) |
| `state` | `ALARM` — есть, `RETURN` — причина ушла, не квитирована, `ACCEPT` — квитирована, причина есть |
| `suppressed` | подавлена |

Статус узла: нет связи — `BadCommunicationError`; ответ прошивки не разобран — `BadDecodingError` (прежний список за свежий не
выдаётся, ошибка в журнале раз в минуту).

Метод `ns=2;s=SYSTEM.ALARM_CMD` (объект `ns=2;s=SYSTEM`), аргументы `Action` (String: `ACCEPT`, `SUPPRESS`, `UNSUPPRESS`),
`ObjectType`, `ObjectNumber`, `AlarmNumber` (Int32) — команда прошивке
`errors_manager:get_instance():set_cmd( <100|200|201>, <ObjectType>, <ObjectNumber>, <AlarmNumber> )`. Исход: `Good` — прошивка
выполнила строку; `BadInvalidState` — ошибка Lua в прошивке; `BadCommunicationError` — нет связи; `BadInvalidArgument` — неизвестное
действие или не те типы аргументов; `BadUserAccessDenied` — роль `read`.

Поведение прошивки (сверено с исходниками ptusa и на эмуляторе):

- `Good` не значит, что авария нашлась: команду над уже ушедшей аварией прошивка молча пропускает; итог виден по следующему списку;
- сообщение объекта (`objectType` ≥ 100) любая из трёх команд удаляет; у устройства `ACCEPT` переводит `ALARM` в `ACCEPT`, а `RETURN`
  убирает, номер аварии не используется;
- у объекта не больше 10 сообщений: новые сверх этого прошивка теряет, пока старые не квитированы;
- ошибки устройств и объектов прошивка отдаёт через 5 с (параметр `P_POST_START_ERROR_PROCESSING_DELAY_MS`) после первого запроса
  списка, пока есть критическая ошибка связи — только критические;
- описания прошивка не экранирует: кавычка `"` в тексте сообщения делает весь ответ неразборным (`BadDecodingError`).

Тесты: `cargo test` — разбор снимка и песочница, конфигурация станции (1834 канала), сценарий
целиком (`tests/facade.rs`: фейковый PAC в проводном формате ptusa + настоящий OPC UA-клиент: чтение,
запись, отказы, обрыв и восстановление связи, ядовитый снимок, аварии и их квитирование; защита — вход с паролем, отказ анониму,
неверному паролю и чужому сертификату, запись и действия над авариями только с ролью `write`). Песочница и клиент PAC — копии
`src/sandbox.rs` и `src/pac/` шлюза: при исправлении уязвимости править оба места.
